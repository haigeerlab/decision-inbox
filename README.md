# decision-inbox

多会话协作时的决策收件箱。几个 Claude Code 和 Codex 会话一起干活时，要你拍板的事、谁在等谁、谁停下了，都集中到一个「收件枢纽」会话里：

- **待答表**：各会话抛来的【等待用户】事项，按挡住几条线排序，一项一张卡片，推荐选项带好复制块；你回「12 A」，收件枢纽原话转达给提出方（多线事项分别转给各条线）。
- **等待单**：谁在等谁的什么、等了多久，只按四种理由关单。
- **巡视**：按每 5 分钟设定（实际间隔受宿主影响，见排查），停下或空闲积压的 Claude 会话先叫醒，叫不醒或全线停住时发桌面通知。定时任务没按时跑时，收件枢纽会顺带巡视：它被叫醒或你跟它说话时，巡视超过 10 分钟没跑就补一轮（通知直接显示在收件枢纽里）。
- **停止钩子**：有会话在等你时，工作会话收工前会被拦一次，提醒先交付或报阻塞。
- **查询**：各线状态、流畅度体检、单项时间线、能力图进度。

依赖：

- [agent-relay](https://github.com/haigeerlab/agent-relay)：会话之间的邮箱，必需；
- [spec-guard](https://github.com/haigeerlab/spec-guard-plugin)：可选，有了才能看能力图进度和进度预警；
- macOS、`python3`（3.10 及以上，只用标准库）、Claude 桌面版（收件枢纽和巡视任务都在桌面版里跑）。

## 安装

发布前从本地目录安装（把 `<仓库目录>` 换成这个仓库在你机器上的路径）：

| Claude Code | Codex |
|---|---|
| `/plugin marketplace add <仓库目录>` | `codex plugin marketplace add <仓库目录>` |
| `/plugin install decision-inbox@decision-inbox-marketplace` | `codex plugin add decision-inbox@decision-inbox-marketplace` |

装好后开一个新会话，插件的命令、技能和钩子才会生效。

### 固定副本安装（演练与接入用）

从开发目录安装时，开发目录一变，装好的插件就跟着变。演练和正式接入要用一个不会再变的副本，两个宿主都从它安装：

1. 在仓库里给要冻结的提交打标签，再检出一个独立副本：`git tag v<版本>`，`git worktree add --detach <副本目录>/v<版本> v<版本>`。
2. 两个宿主都把 `decision-inbox-marketplace` 指向这个副本目录，再重装插件：
   - Claude Code：`claude plugin marketplace remove decision-inbox-marketplace`，`claude plugin marketplace add <副本目录>/v<版本>`，`claude plugin install decision-inbox@decision-inbox-marketplace`；
   - Codex：`codex plugin marketplace remove decision-inbox-marketplace`，`codex plugin marketplace add <副本目录>/v<版本>`，`codex plugin remove decision-inbox@decision-inbox-marketplace`，`codex plugin add decision-inbox@decision-inbox-marketplace`。
3. 重开会话，在不属于任何插件仓库的目录里运行 `doctor`：「Claude、Codex 两边的版本」应为同一个版本，「转发脚本」指向副本目录。

Codex 会把装好的副本缓存在自己的目录里，只改市场不重装，Codex 会话仍跑旧版；启动时它还会把转发脚本切到自己那一份。所以两边一定都要重装，并用 doctor 核对。

## 接入

已经在项目规则文件里手贴过收件枢纽规则的，接入前先删掉手贴的旧收件枢纽规则，只保留约定块这一份来源。

按这个顺序接入，每一步都会先预览要写哪个文件、写什么，你确认后才写：

1. **收件枢纽**：为它单独建一个目录，在这个目录里开一个 Claude 桌面版会话，运行
   `/decision-inbox:hub-setup <协作组名> <它在 agent-relay 的身份名>`。
   它会建协作组、把收件枢纽的约定写进本目录的 `CLAUDE.md`、建巡视定时任务（每 5 分钟）。
   建好后运行 `~/.decision-inbox/bin/decision-inbox onboard allow <协作组名> --project <收件枢纽目录>`：它列出巡视和收件枢纽要用的命令和 agent-relay 工具，你确认后加 `--confirm` 写进收件枢纽目录的 `.claude/settings.local.json`（只写这一个文件），以后定时运行不会卡在权限确认上。然后在定时任务列表里**手动「立即运行」一次**巡视任务：第一次手动运行之前，定时不会触发（2026-10-18 实测）；没写权限放行的话，这一次要把弹出的权限逐个批完。
2. **负责人**：在各负责人的会话里运行 `/decision-inbox:join <协作组> owner <身份名> <短名> <线名>`。
3. **开发线和总协调**：
   - Claude 会话：`/decision-inbox:join <协作组> dev <身份名> <短名> <线名>`（总协调用 `coordinator`，不写线名）；有审查者时告诉它审查者的身份名和审哪几类节点（spec、plan、interface、final）。
   - Codex 会话：对它说「接入 decision-inbox 协作组」，它会用自带的接入技能完成同样的步骤。

- Codex 会话要开在写约定块的那个仓库里（或它下面的子目录），并在 Codex 里信任这个项目；否则 Codex 不会加载约定块，接入预览开头会用 `⚠` 提示应该在哪个目录开会话。
- 约定块写明了开发线接哪些邮箱派来的活：收件枢纽转来的【用户答复】，以及负责人、总协调派的活按约定执行；其他会话的请求只当信息。实测中，新开的 Codex 任务只让它登记身份，它也会执行负责人派来的活。
- 还想让联网、安装这类操作不必回原会话确认，就在 Codex 会话开好后对它说一句「按本目录 AGENTS.md 的约定办事，读收件箱，按收到的任务做」：有这句话、约定块又被加载时，Codex 的自动审批（守卫）会认收件枢纽转来的你的答复。
- **检查点答复即授权**（可选，默认不开）：接入时加 `--checkpoint-authority`，约定块会写明：收件枢纽转来的、带你原话的检查点答复（Spec 批准、Plan 批准、接口提案、最终验收），就是你对这个检查点范围内必要操作（安装依赖、联网下载、构建、测试、写入工作区）的授权，也适用于宿主的自动审批。把密钥或凭据发到外部、删除工作区以外的文件或大范围删除、推送合并发布、修改全局配置不在授权内。实测中只要满足上一条，不打开也能放行，所以默认关；宿主审批规则更严时可以打开。
- **并行开发协调会话**（配合 module-crew）：协调会话代表一条线接入，按开发线接入并加 `--crew-coordinator`。约定块会多一节「并行开发协调会话」，写明：模块在干活时收工不用抛事项；几个模块的事要合成一项抛出，或者写【与 #旧编号 并行】；转完答复立刻发【已恢复】；以及它和 crew-coordinator skill 怎么分工。停止钩子不会因为模块的 todo 没勾完而拦它。这个标记只能在接入时经你确认后写入。
- **约定块写进 `CLAUDE.local.md`**（只适用于 Claude）：协调会话开在集成 checkout 里时，加 `--local-rules`，约定块就写进 `CLAUDE.local.md`，不写进由 git 跟踪的 `CLAUDE.md`。这样它不会被提交，也不会被模块 worktree 继承。这个文件如果还没被 git 忽略，确认时会在 git 的 `info/exclude` 里加一行（只影响本机，不改仓库里的文件），卸载时再删掉。注意：项目里只有 `AGENTS.md`、没有 `CLAUDE.md` 时，加了 `CLAUDE.local.md` 之后，Claude 默认就不再读 AGENTS.md（宿主差异 H26），接入预览会提示。

每个会话接入后还要做两件事（命令会提示）：

- 在 agent-relay 登记身份并绑定唤醒（`bridge_register`，`wake: "auto"`）；
- 在 Claude Code 和 Codex 里各信任一次插件自带的停止钩子。

约定会写进各项目的 `CLAUDE.md`（Claude）或 `AGENTS.md`（Codex），用 `<!-- BEGIN decision-inbox … -->` 和 `<!-- END … -->` 包住，块外的内容一字不动；重复接入会整块替换。

### 替换已有的收件枢纽

原来已经有一个收件枢纽（比如手贴规则版）在用、并且编过号时，新收件枢纽接入时加 `--start-number <起始编号>`（例如 1001），事项和等待单就从这个号开始编，不会和旧编号混在一起。起始编号只能在新组还没编过号时设；重跑接入可以带同一个值。

切换前，先让各会话把未读消息处理完：新收件枢纽会把当下的未读积压照常算进主视图和巡视。agent-relay 里的历史「欠回复」（`owesReplies`）本插件不读，切换后不会显示成积压。

### 迁移期：还没接入的会话

原来有一套手写规则在跑、各线分批切换时，还没切换的开发线先用 `~/.decision-inbox/bin/decision-inbox onboard enroll <协作组> --relay-name <身份名> --short-name <短名> --host <宿主> --line <线名>` 登记进名册（预览后加 `--confirm`）。这一步只写名册，不写约定块，条目标为「旧格式」。在它正式接入之前：

- 收件枢纽发给它的答复用旧规则认得的编号写法：普通答复写 `事项：#<它那条消息的邮箱号>（hub 编号 N）`，多线答复写 `事项：#<发起方那条消息的邮箱号>（多线事项，发起方 <身份名>；hub 编号 N）`；
- 不给它发【答复告知】（旧规则里没有这种消息），负责人的决定仍按旧路线转交给它；
- 它用自己的邮箱号写的【取代】【撤回】，收件枢纽也认（只限它自己还没结束的事项）。

它以后用 `/decision-inbox:join` 正式接入时，「旧格式」标记自动去掉，从此用正式写法。要把它移出收件范围，就用 `onboard leave`：名册条目保留，收件枢纽不再给它发任何消息。leave 的预览会列出它名下还没结束的事项和开着的等待单。doctor 对这类条目报「只登记，不写约定块」，属正常。

## 日常使用

平时只看收件枢纽，直接对它说话：

| 你说 | 它做什么 |
|---|---|
| `12 A`、`12 B 但先别上线`，或复制卡片里的推荐块 | 把你的原话转达给提出方 |
| `21 A；D1 B；D2 A` | 事项带「待你决定的问题」（D1、D2…）时，主选项和每个 D 都要答；少答、答错字母会被追问，不会转发半截答复，也不会按审查倾向替你默认 |
| 复制主视图末尾「一次答完（全按推荐）」的代码块 | 几项同时等你时，一次全按推荐答完 |
| `12 详情` | 显示事项全文、各线范围和消息编号 |
| `看等待`、`看已关闭`、`看已关闭 2026-10-15`、`看失效` | 展开对应明细 |
| `关掉 #5 已经不需要` | 按「用户关闭」关掉等待单；「看等待」里标着「可能已失效」的单（发送方之后又发过消息、却没结束它；新开的【等待其他会话】不算，并行开发协调会话的单不做这个判断），通常就是这样关掉 |
| `重发` | 重新列出没发出去的消息 |
| `以后 X 都这样` | 先问你发给哪几个会话，确认后原话转过去 |

查询命令（只读，不给任何会话发消息）：

- `/decision-inbox:lines`：各线状态；
- `/decision-inbox:flow`：流畅度体检，卡在哪、谁等谁；
- `/decision-inbox:item <编号>`：单项时间线；
- `/decision-inbox:map [线|all] [全部]`：能力图进度；评审列写「通过／待审／改后待复审／不适用／异常」，有外部审查参考意见时加「（有参考意见）」。

体检与统计（命令行，只读）：

- `~/.decision-inbox/bin/decision-inbox doctor [--group <协作组>]`：逐项核对约定块是不是当前版本、转发脚本指向、巡视、Codex 能否加载约定块、Codex 钩子信任、依赖插件版本与接口（module-crew 另写契约版本；名册里有协调会话时，还实际读一次它的只读出口，报读到几个模块或读不到的原因）；每项写来源和怎么做，有异常时退出码 3。`--json` 给程序读（`schemaVersion` 1，字段 `name`、`state`、`source`、`evidence`、`fix`），`--report` 出一份可以直接转给负责方的异常报告（不含消息正文）。
- `… query stats <协作组> [--since 2026-10-17] [--json]`：事项数、绕过收件枢纽结束的事项、抛出→答复与答复→恢复的耗时（中位、最长）、被取代／退回／追问被退回／拒收转述次数、开着的等待单、巡视实际跑了几轮和相邻两轮的最长间隔。
- `… query events <协作组> --json [--since <日期>]`：事件日志，每条固定为 `at`、`kind`、`actor`、`item`、`data`。

### 并行开发线在主视图里怎么显示

接了 `--crew-coordinator` 的协调会话，代表一条由 module-crew 并行开发的线。主视图、`/decision-inbox:lines` 和巡视会在它的仓库里运行 module-crew 在 `interface.json` 里发布的只读出口（`sessions --json`，只认接口 1.x、schemaVersion 1，3 秒超时），列出各模块，不读 module-crew 的状态库：

- module-crew 0.3.0 起出口带审查状态时，模块写「返工中（审查第 N 轮）」或「审查中」，取代阶段词；旧版本没有这个字段，照旧显示阶段；
- 只要有一个没挂起的模块会话在忙（按 agent-relay 的忙闲），这条线就是「干活中」，不算阻塞，也不参与「全线互等」；协调会话开着的等待单全部写在括号里，例如 `干活中（模块 a 在忙·构建、b 停着·等合并、c 挂起：等接口；还在等 API #1203、#1204）`；
- 没有模块在忙时，照常按协调会话的等待单判阻塞、参与全线互等，括号里照样列出模块；
- 出口读不到时写「模块状态未知：原因」，这时不报全线互等；
- 这条线不判「停住」，模块进度归 module-crew。

回复里只有不带字母的数字（`21`、`#21`）是事项号。交审编号 `C15`、审查编号 `R-3`、问题编号 `D1` 都原样留在你的原话里转过去，不会被当成别的事项；`21 B，C15 退回` 这样写，认作答 #21 选 B。

收件枢纽收下一项【等待用户】后，会静默回发件会话一条【登记回执】：事项号、取代了哪几项、写法提示（缺「项目」、你该回只写字母等）。发件会话写【取代】【撤回】时用回执里的事项号。迁移期还没接入的会话不发回执。

收件枢纽不替你决定、不改写选项、不批宿主的权限确认；要你去某个会话里亲手点确认时，它会明说。

收件枢纽只认你在它的会话里亲手输入的话。别的会话发来的消息（包括替你传话的测试或协调会话）不会被当作答复，它会提示你亲手再说一遍。注意：程序看不到一句话是谁输入的，这一层靠收件枢纽遵守约定来判断来源。

开发线对答复有疑问时，收件枢纽会自动回一条固定说明（写明事项编号和它自己的原消息编号的对应关系），并在主视图的异常里记一行；它不会自己答疑。

负责人抛的事项被你答复后，收件枢纽会给这条线上的开发线各发一条【答复告知】：只是让它们知道答复已经有了，不是批准，开发线要等负责人转交后才执行。

## 消息协议

各会话之间的消息格式（【等待用户】【用户答复】【等待其他会话】【已恢复】【撤回】【审查结论】【答复告知】、结束写法、问题代码等）以共用契约 `session-protocol` v2.0.1 为准，本插件的测试里逐份跑契约样例（`tests/fixtures/session-protocol/v2.0.1/`）。v2.0 起有【登记回执】、【等待用户】与【审查结论】的「待用户决定」、「有须修改项N条」与「须修改」，以及编号前缀（C／R／D）；【审查结论】改由审查者交给协调会话，可以静默抄送收件枢纽，收件枢纽只数审查轮次，不据此产生事项。0.0.21 起钉 v2.0.1，module-crew 要同为 2.x，doctor 才报兼容（0.2.x 讲 1.9，会报不兼容，要和 module-crew 0.3.0 一起换）。v1.1 起契约里另有【交审】【公共变更请求】【协调通知】三种消息，供多模块并行开发的插件使用；本插件不解析【交审】【公共变更请求】【协调通知】，一致性测试跳过这三类。v1.6 起另有【负责人转交】（负责人发给本线的开发线或总协调），以及总协调转给开发线的、带「转自」的【用户答复】。收件枢纽收不到这两种，一致性测试也跳过它们。协议要改时先改契约，再改本插件；契约的改动由用户批准。

## 使用注意事项

| 现象 | 原因（来源） | 你怎么做 | 有问题找谁 |
|---|---|---|---|
| 收件枢纽或负责人一阵子没反应 | Claude 桌面版会停掉空闲会话，agent-relay 叫不醒（宿主） | 巡视会用会话消息工具叫醒；巡视也停了就手动点开 | 巡视叫不醒时找本插件 |
| 主视图写「巡视 N 分钟没跑」 | 两种可能：定时任务停在权限确认上；或宿主没按时触发（周期任务实际间隔不规律，宿主差异 H24） | 去定时任务列表看最近一次运行：停在权限确认上就批完（或运行 `onboard allow` 放行）；没有在跑的就立即运行一次 | 宿主限制；放行后仍停在权限确认：本插件 |
| 重启 ChatGPT 后 Codex 线都不动 | Codex 会话不会自动加载（宿主） | 逐个点开协作中的 Codex 会话 | 宿主限制 |
| Codex 开发线不按约定办事 | 会话开在接入的仓库之外，约定块没被加载（宿主） | `doctor` 看「Codex 加载约定块」，在接入的目录里新开任务 | doctor 报得不对时找本插件 |
| 读收件箱提示身份不是本会话 | Codex 会话丢了联调身份（agent-relay） | 按提示用原名重新登记 | agent-relay |
| 主视图异常区写「送达存疑」 | 对方接受了唤醒却一直没读，多半是任务的信箱连接断开（agent-relay 0.8.2 起标出） | 完全退出 ChatGPT 再打开那个任务 | agent-relay |
| 开发线要你回原会话确认 | Codex 自动审批不认转来的批准（宿主） | 收件枢纽会把它列成事项；去原会话亲手确认 | 宿主限制 |
| 收件枢纽某条命令被拦下 | Claude 自动模式拦了这类命令（宿主） | 按收件枢纽讲的原因处理，不要换写法绕过 | 宿主限制 |
| 报「全线停住」但有线在干活 | 旧等待单没关；发送方后来又发过消息的单会标「可能已失效」，不计入（本插件设计；新开的【等待其他会话】不算，协调会话的单不做这个判断） | 「看等待」，关掉不需要的单 | 本插件 |
| Claude 会话不按项目的 `AGENTS.md` 办事 | 项目只有 `AGENTS.md`，又加了 `CLAUDE.local.md`，Claude 就不再读 AGENTS.md（宿主差异 H26） | 在项目里放一个 `CLAUDE.md`，写一行 `@AGENTS.md` 导入；或者在 Claude 设置里让它两种文件都读 | 宿主限制 |
| `doctor` 报某个依赖插件「读不到接口说明」 | 那个插件的版本早于提供 `interface.json`（依赖插件） | 升级那个插件 | 那个插件 |
| 不知道问题该报给谁 | — | 运行 `doctor --report`，按每项的「来源」转给负责方 | — |

## 升级

| Claude Code | Codex |
|---|---|
| `claude plugin marketplace update decision-inbox-marketplace`，再 `claude plugin update decision-inbox@decision-inbox-marketplace` | `codex plugin marketplace upgrade` |

升级后开一个新会话即可。约定块和巡视任务调用的是固定路径 `~/.decision-inbox/bin/decision-inbox`，插件在会话开始时会自动把它指向新版本，不用重新接入。

例外：约定块本身改了的版本，要在收件枢纽里重跑一次 `/decision-inbox:hub-setup`、各工作会话重跑接入，拿到新约定块（`doctor` 会提示「约定块不是当前版本」）。0.0.14 的收件枢纽约定块加了「顺带巡视」，0.0.15 改用单独的 `patrol-agents.json`。0.0.16 只给加了 `--crew-coordinator` 的会话多出一节，已经接入的会话不用重跑。0.0.17 改了负责人、开发线、总协调的约定块（写明【负责人转交】），已经接入的会话都要重跑接入。0.0.18 没改约定块，不用重跑。0.0.19 也没改约定块，不用重跑。

0.0.20 没改约定块，但巡视改了写法：中间文件放到 `~/.decision-inbox/<协作组>/io/`，桌面通知改用 `decision-inbox notify`。升级后在收件枢纽里做两步，每步都先预览、你确认后才写：
1. 重跑 `~/.decision-inbox/bin/decision-inbox onboard allow <协作组> --project <收件枢纽目录>`，放行清单会多一条 `Edit(//…/.decision-inbox/<协作组>/io/**)`，巡视写中间文件就不用再等你点确认；
2. 运行 `~/.decision-inbox/bin/decision-inbox patrol prompt <协作组>` 拿新的巡视提示词，让收件枢纽用它更新定时任务 `decision-inbox-patrol-<协作组>`（定时任务工具 update_scheduled_task；会先给你看要改成什么）。

0.0.21 改了约定块（开发线、负责人、总协调写明【登记回执】、「待用户决定」和编号前缀；收件枢纽写明 `wake` 照填），契约改钉 v2.0.1。升级后：
1. 收件枢纽重跑一次 `/decision-inbox:hub-setup`，各工作会话重跑接入，拿到新约定块（`doctor` 会提示「约定块不是当前版本」），然后各自新开会话；
2. module-crew 一起换成 0.3.0（讲契约 2.x）；只换一边时，doctor 的「依赖：module-crew」会报契约主版本不一致。

## 卸载

1. 在各工作会话里运行 `/decision-inbox:leave`（Codex 会话说「退出 decision-inbox 协作组」），删掉规则文件里的约定块。
2. 在收件枢纽里运行 `/decision-inbox:teardown`，删掉它的约定块和巡视定时任务。
3. 卸载插件：Claude Code 用 `claude plugin uninstall decision-inbox@decision-inbox-marketplace`；Codex 用 `codex plugin remove decision-inbox@decision-inbox-marketplace`。

`~/.decision-inbox` 下的状态目录（名册、事项、等待单、事件日志）**保留**，不会被删除；确实不要了再自己处理。

## 排查

| 现象 | 先看 |
|---|---|
| 收件枢纽欠回复越来越多（`bridge_agents` 里 `owesReplies` 只增不减） | 被取代、被撤回的【等待用户】没人回。0.0.9 起收件枢纽答复时用 `alsoAnswers` 一并关掉，开发线取代或撤回时用 `withdraws`；已接入的会话要重跑接入命令拿到新约定块（agent-relay 0.8.0 起支持） |
| doctor 报「Claude、Codex 两边的版本」异常 | 两个宿主各自装了一份 decision-inbox，版本不同，或 Codex 缓存里留着旧版本：按这一项的「怎么做」两边重装，再重开会话。转发脚本跟着最后启动的那个宿主走，版本不一致时两边会来回切换 |
| leave 预览写「还有没了结的事」 | 这个会话抛出的事项还没结束，或它还开着等待单。leave 照常执行，但这些事项会留在主视图里：事项最好在 leave 前由它自己发【撤回】，等待单你可以在收件枢纽说「关掉 #编号」 |
| 会话刚做完一轮，主视图就写「掉线」 | 0.0.20 起，桌面版收起空闲会话（agent-relay 报 `stopped`）时，只要登记了桌面会话编号或有唤醒绑定，就不算掉线，按其他情况判断；模块会话写「停着」。仍写「掉线」的，是叫不醒的：没登记 `--desktop-session`、没有唤醒绑定，或者 Codex 任务没打开 |
| 巡视运行一直「运行中」，后面的运行都没跑 | 多半卡在权限确认上：上一次没跑完，宿主会跳过之后到点的运行。打开那次运行的会话批完；升级到 0.0.20 后按「升级」一节重跑 `onboard allow`、换上新的巡视提示词，巡视就不再需要确认 |
| 不确定装对没有 | 运行 `~/.decision-inbox/bin/decision-inbox doctor`，按每项的「怎么做」处理 |
| 停止钩子不拦 | 在那个会话的工作目录运行 `~/.decision-inbox/bin/decision-inbox whoami`：退出码 4 是没接入，5 是同一个目录对上了多个协作组；钩子出任何问题都会放行，不会卡住会话 |
| 主视图第一行写「巡视还没跑完过一轮」或「巡视 N 分钟没跑」 | 在定时任务列表里打开这个任务：最近一次运行停在权限确认上，就批完；没有在跑的运行，是宿主没按时触发，立即运行一次。`query stats` 能看到这段时间巡视实际跑了几轮、最长隔多久 |
| 收件枢纽跑 `inbox reply --relayed-from` 被自动模式拦下 | 转来的话同样不生效，只是少记一条事件；要留记录，请在收件枢纽会话里批准这一次 |
| 巡视不跑 | 在定时任务列表里看任务是否启用、最近的运行记录；建好后是否手动「立即运行」过一次（第一次手动运行之前，定时不会触发） |
| 收件枢纽换了会话、沿用原身份名接入时 `bridge_register` 被拒 | 名字还绑在旧会话上（agent-relay）：旧会话不用了就同意接管，收件枢纽会带 `takeover` 重新登记 |
| 主视图写「X 空闲，有 N 条消息没读」 | agent-relay 那次唤醒没生效；0.0.12 起巡视在消息放了 5 分钟后叫醒 Claude 会话（含收件枢纽），叫不醒会通知你；Codex 任务要你手动打开 |
| 主视图第一行写「本次没带 agent-relay 状态」 | 这一轮没读 agent-relay，各线状态无法判断；让收件枢纽按约定先读状态再显示 |
| 主视图第一行写「读不到 agent-relay（原因）」 | 读了但解析失败：agent-relay 是否在运行、收件枢纽是否登记了身份 |
| 主视图写「有 N 条消息没发出去」 | 对收件枢纽说「重发」 |
| 命令提示找不到 `~/.decision-inbox/bin/decision-inbox` | 收件枢纽还没接入；或开一个新会话，让插件重新写一次 |
| 状态文件出问题 | 运行 `~/.decision-inbox/bin/decision-inbox store show <协作组>` 看一致性检查 |
