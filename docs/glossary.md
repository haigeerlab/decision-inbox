# 术语表（v1.1，2026-10-19，用户决定 48）

> v1.1：更正 v1 把等待记录标成 R 前缀的错误。契约 v2.0 里 R 是审查编号，等待记录改用 W（契约负责人指出）。

适用于 spec-guard、agent-relay、module-crew、decision-inbox 四个插件和 session-protocol 契约。给用户看的文字、文档、命令说明一律用这里的「名称」。
「旧称」只用于对照：契约里的消息标签和代码标识符暂时保留旧写法，显示时换成新名称；契约标签什么时候改，由契约负责人评估（涉及主版本就留到观察期以后）。

## 一张图看全流程

```
                        跨线协调（只管跨线的事）
                              │
开发线 A ──┐                  │
开发线 B ──┼── 待决事项 ──→ 决策收件箱 ──→ 你
项目 X 的模块协调 ──┘                ↑ 答复原样转回
   │  ↑
交审  │ 送审 ⇄ 审查者（挂在这一层旁边）
   │
模块会话 alpha / beta …
```

模块的一次审批：交审（模块会话 → 模块协调）→ 送审（→ 审查者）→ 审查结论 → 提请批准（→ 决策收件箱）→ 你答复 → 原样转回。

## 一、会话与角色

| 名称 | 定义 | 例子 | 旧称 |
|---|---|---|---|
| 决策收件箱 | 把所有要你决定的事集中到一处的会话：原样展示要审的内容、补上背景、把你的答复原样转回去。它不审查、不替你决定 | 「di-p0 决策收件箱（演练）」 | 收件枢纽、hub |
| 开发线 | 一条独立的开发方向，通常对应一个仓库或一块职责，用线名称呼 | 前端线、API 线、后台线 | 线、dev |
| 线名 | 开发线在协作组里的名字，要让人一看就懂；多线事项的「适用的线」写它 | 「前端」「API」「crew-rehearsal」 | 短名、shortName（如「并行协调2」） |
| 跨线协调 | 负责跨开发线的事：一条线要另一条线配合、多线共同执行的决定。不转交审查 | LIVE-SAAS 的跨线协调会话 | 总协调、coordinator |
| 模块协调 | 一个项目里统筹多个模块会话的会话：收交审、送审、提请批准、合并。显示时带项目名 | 「crew-rehearsal 的模块协调」 | 协调会话、并行协调、crew coordinator |
| 模块会话 | 只负责一个模块、在自己的 worktree 里开发的会话，只和模块协调说话 | rh2-alpha | — |
| 审查者 | 登记在开发线（或模块协调）旁边，对 Spec、Plan、接口、最终验收做技术审查的会话；也可以发起多线事项 | live-saas-arch-review | 负责人、owner、lead、审查会话 |
| 邮箱名 | 会话在本机邮箱（agent-relay）里的地址，发消息时用 | rh2-coord | 身份名、relayName |
| 协作组 | 共用一个决策收件箱的一组开发线 | di-p0 | — |
| 名册 | 协作组里登记了哪些会话、各自什么角色和线名 | — | — |

「插件负责人」只指开发某个插件的会话，只在插件开发时使用，不出现在给你看的内容里。

## 二、要你处理的东西

| 名称 | 定义 | 例子 | 旧称 |
|---|---|---|---|
| 待决事项 | 决策收件箱里一件等你决定的事。编号是 #数字，只有它用 #数字 | #21 | 事项 |
| 交审 | 模块会话交给模块协调的一份审查申请，节点是 Spec、Plan、接口或最终验收之一。编号带 C 前缀 | C15 | — |
| 提请批准 | 模块协调把交审连同审查结论送到决策收件箱，成为一件待决事项。一次一个模块 | — | 合批 |
| 多线事项 | 同时影响几条开发线的待决事项，你的答复会分别发到各条线，各附它自己的范围 | #22 | — |
| 适用的线 | 多线事项影响哪几条开发线，填线名 | 「前端、API」 | 适用会话 |
| 待你决定 | 审查或交审里列出的、必须你拍板的问题。编号带 D 前缀，漏答会被追问，不会按倾向默认 | D1 首字母大小写 | 待用户决定 |
| 等待记录 | 某个会话在等别的线或别的模块时记下的一条，等到了就关掉。编号带 W 前缀 | W3 | 等待单 |

## 三、流程动作

| 名称 | 定义 | 旧称 |
|---|---|---|
| 送审 | 模块协调（或开发线自己）把交审发给审查者；默认不经跨线协调 | — |
| 审查结论 | 审查者的结论：通过、通过并附建议、有须修改项（退回本层改）、待你决定。每份审查有审查编号，带 R 前缀，如「审查 R-7（交审 C15）」 | — |
| 返工 | 审查给出须修改项后，模块协调把交审退回模块会话修改，不经过你；带轮次，超过上限才交给你 | — |
| 你的答复 | 你在决策收件箱的回复，原话一字不改转回 | 用户答复 |
| 答复告知 | 审查者发起的单线事项被答复后，同线其他会话收到的知会（内部机制，不出现在你的视图里） | — |
| 审查者转交 | 审查者把你的答复按路线转给执行的会话 | 负责人转交 |
| 已结项 | 发起方表示「挡住我的事已解决，这一项结束」 | 已恢复（契约标签暂保留【已恢复】） |
| 开工通知、退回通知、返工通知、撤销批准通知 | 模块协调发给模块会话的指令，显示时直接写类型 | 协调通知 |
| 可信批准来源 | 模块协调只认这些来源转来的批准（通常是决策收件箱） | 批准来源、登记来源 |
| 原话 | 你亲手打的那句话，原样存档作为授权依据 | 开工原话 |
| 巡视 | 决策收件箱定时检查、叫醒停住的会话 | — |
| 挂起／恢复 | 让一个模块暂停让位、之后再继续（和「已结项」无关） | — |
| 撤回批准 | 合并前收回已经给出的批准 | — |

## 四、开发对象

| 名称 | 定义 | 旧称 |
|---|---|---|
| 能力图 | 一个项目拆成哪些模块、依赖和开发顺序 | — |
| 模块 | 能力图里的一块能力，有自己的 Spec、Plan | — |
| Spec（规约）、Plan（计划）、todo（任务清单） | 做什么、怎么做、做到哪了 | — |
| 检查点 | Plan 里约定停下来核对的点；批 Plan 时可写「检查通过就继续」 | gate |
| 最终验收 | 模块做完后批准合进集成分支的节点 | final |
| 集成分支 | 各模块最终合进去的那条分支，括号写分支名，如「集成分支（main）」 | 集成基线、baseline |
| 批准标记 | 写在 Spec、Plan 文件里、表示你已批准的那一行标记 | 评审标记 |
| 评审节奏 | 项目配置：分开审（默认，先 Spec 后 Plan）或一起审 | reviewCadence |
| 协作规则段 | 写进项目规则文件（CLAUDE.md、CLAUDE.local.md、AGENTS.md）的一段协作规则 | 约定块 |

## 五、用词统一
- **审查**：审查者做的技术检查。
- **批准**：你做的决定。
- **验收**：只指「最终验收」这个节点。
- 不再用「评审」「审核」「审批」。
- 编号：#数字 只表示待决事项；交审 C、审查 R、待你决定 D、等待记录 W 都带字母前缀（C／R／D 以契约 v2.0 为准；W 是术语表新定的显示前缀，契约里没有，等待记录在契约里出现时按契约写法）。
