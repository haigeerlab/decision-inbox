# 第 ⑥ 阶段：真实协作组实地验收方案（用户 2026-10-18 批准，假设均确认）

> 依据：`docs/requirements-record.md` 第 12 节第 16 项——六阶段的最后一步：「在真实协作组替换规则版收件枢纽做实地验收，发 0.1.0」。
> 本方案只描述做法，批准前不碰真实协作组。文中「真实协作组」指用户选定的那个协作组，项目名不写进仓库。

## 假设（请先确认）

1. **验收组**：在一个正在真实开发的协作组里做，它现在用的是手贴规则的收件枢纽（规则版）。
2. **规则版的规则原文不在收件枢纽目录里**：盘点时要先找到它（可能在会话里手贴、或在别的目录的规则文件里），存档后才能切换和回退。
3. **参与会话**：收件枢纽（Claude 桌面版）、总协调、若干开发线（Codex 桌面版）、审查或负责人会话（Claude 桌面版）。每个会话的角色由用户在盘点结果上确认。
4. **验收期间正常开发不停**：本插件只改各项目规则文件里的约定块和插件安装，不改项目代码。
5. **要改用户配置的步骤由用户操作或逐项授权**：Codex 里安装 decision-inbox 并信任停止钩子、收件枢纽目录的权限放行、定时任务。
6. **观察期 2 个工作日**，期间至少要有 10 项经收件枢纽的用户决定，样本才算够。

## 阶段

### P0 准备（不动真实协作组）

- 在 Codex 里安装 decision-inbox 插件，并用命令行版 codex 信任它的停止钩子（宿主差异 H8）；`decision-inbox doctor` 的「Codex 钩子信任」变为 ✔。
- 在一个新的小测试组里补做三项没实测的：S1 负责人离线时巡视自动叫醒；S3 Codex 停止钩子拦「有人在等却收工」；答复带 `alsoAnswers` 后收件枢纽的 `owesReplies` 回落。任一项失败先修再往下走。
- 产出：三项实测记录、doctor 全绿（测试组）。

### P1 盘点（只读）

- 找到规则版收件枢纽的规则原文，和各会话规则文件里手贴的相关段落，原样存档到收件枢纽目录外的私有位置（不进本仓库）。
- 列出：各会话的 agent-relay 身份名、宿主、工作目录、角色、所属线；规则版里还没答的事项；各身份的 `owesReplies`、`waiting`。
- 产出：一张会话清单和一份未答事项清单，交用户确认角色与线的划分。

### P2 切换（一次完成，开始前用户再确认一次）

1. **清空旧待答**：规则版里还没答的事项，由用户在旧收件枢纽答完，或标作废、让提出方切换后重抛；不让两套并存。
2. **收件枢纽**：沿用原 agent-relay 身份名（各会话不用改收件人）；新会话登记这个名字会因名字还绑在规则版收件枢纽会话上被拒，要用户同意接管（2026-10-18 P0 实测）；在收件枢纽目录新开 Claude 会话，运行 `/decision-inbox:hub-setup`；建巡视定时任务；`onboard allow` 预览并经用户确认写入权限放行；手动「立即运行」一次巡视。
3. **其余会话**：先负责人／总协调，再开发线，逐个 `/decision-inbox:join`（Codex 线说「接入 decision-inbox 协作组」）；接入前删掉手贴的旧收件枢纽规则；Codex 线接入后新开任务，让它加载约定块（宿主差异 H18）。
4. **核对**：`doctor` 除已知项外全绿；收件枢纽主视图能列出各线状态。
   - 分批切换时，还没切换的开发线先用 `onboard enroll` 登记为旧格式（0.0.17 起）：收件枢纽对它用旧编号写法，它正式接入后自动换成正式写法。
5. 规则版收件枢纽会话停用（不删，留着回退）。

### P3 观察（2 个工作日）

每天收工前存一份 `doctor --report` 和 `query stats --json`（存在私有位置），按下面的指标记一行（巡视节奏用 `query stats` 的巡视一行）：

| 指标 | 通过线 |
|---|---|
| 答复送达是否准确（送错会话、编号对不上） | 0 次 |
| 绕过收件枢纽结束的事项（`query stats`） | 占比 ≤ 10%，每一项能说清原因 |
| 「全线停住」误报 | 0 次 |
| 巡视卡在权限确认（定时任务列表里最近一次运行停在确认上） | 每天 ≤ 1 次，且 15 分钟内被发现 |
| 宿主没按时触发巡视（`query stats` 的轮数、最长间隔、超 15 分钟次数；宿主差异 H24） | 只记录，不计入通过线；但因此有消息积压超过 30 分钟没人叫醒的，记一次问题 |
| 送达存疑 | 出现后都在当天处理掉 |
| 收件枢纽欠回复（`owesReplies`） | 观察期末不比开始时多 |
| 用户主观：要决定的事是否只在收件枢纽一处看 | 用户认可 |

### P4 判定与发版

- 全部指标过线、用户认可 → 写 CHANGELOG、两份清单升到 0.1.0、更新 README 的「已知限制」；打 tag 和发 GitHub release 是对外动作，单独确认后做。
- 有指标没过线 → 记成新模块需求（按 spec-guard 流程插入能力图），修好后只重跑没过的那部分观察。

## 回退

- **触发条件**（任一）：答复送错会话 1 次；收件枢纽连续 1 小时不可用且巡视没发现；用户判定影响了正常开发。
- **做法**：各会话运行 `decision-inbox onboard leave`（收件枢纽 `teardown`）删掉约定块；把 P1 存档的规则原文贴回原位置；恢复规则版收件枢纽会话；删除巡视任务。协作组状态目录保留，用于分析。
- 回退不影响项目代码和 agent-relay 的邮件记录。

## 风险

- Codex 线新开任务会丢掉旧任务里的上下文：切换前让每条线写一份交接（当前模块、下一步、在等什么）。
- 宿主差异 H1（Claude 会话被停）、H20（定时任务遇新工具就停）、H19（自动模式拦命令）在真实使用中会出现：观察期按 README「使用注意事项」处理，并记进指标。
- 真实项目的名称、路径、事项内容不进本仓库；存档和日报都放在私有位置。

## 要用户做或批准的

- P0：Codex 插件安装与钩子信任；小测试组的实测（含一次在收件枢纽亲手答复）。
- P1：确认会话清单与角色。
- P2：开始切换的确认；收件枢纽目录权限放行的确认；清空旧待答；Codex 线新开任务。
- P4：发版（tag、release）。
