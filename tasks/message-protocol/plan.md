# Implementation Plan: message-protocol

> 依据：`spec/message-protocol.md`（已批准）。任务清单：`tasks/message-protocol/todo.md`。

## Overview

先搭解析骨架（类型识别、开头行、字段切分），把除【等待用户】以外的简单消息一起做完；再分三步加【等待用户】的字段与选项、多线范围、审查状态行；最后做【用户答复】的生成和往返校验。每个任务先写失败的测试，再实现到全绿，单独提交。

## Architecture Decisions

- 全部逻辑在 `decision_inbox/protocol.py`，只用标准库，不依赖 `store.py` 或 `relay.py`（能力图上本模块无依赖）。
- 解析分两段：先把文本切成「开头区」（字段之前的标签行、「结束：」、「回复：」）和「字段区」；字段区按已知字段名切分，每个字段的值一直延续到下一个已知字段名。已知字段名是一张固定表，按消息类型取用；不认识的「X：」行算作上一个字段值的一部分，不当成新字段。
- 「选项与我的建议」的值再细分：以字母 + `：` `:` `.` `、` `)` 开头的行开始一个新选项；选项内以「选了会怎样」开头的行是后果；「推荐 A」「推荐：A」「推荐A」都认作推荐 A。
- 问题和提示统一为 `Issue(code, text)`；代码集合集中写在模块顶部一张表里，测试断言这张表与 Spec 字段表一致，防止漏写或改名。
- 测试样例放在 `tests/fixtures/protocol/*.txt`，每个文件一条完整消息，按需求第 4、6 节的写法构造；变体（删字段、改冒号）在测试里对原文做字符串替换，不另存文件。

## 影响面

新增：`decision_inbox/protocol.py`、`tests/test_protocol.py`、`tests/fixtures/protocol/` 下约 6 个样例文件。修改：`tasks/message-protocol/todo.md`（勾选）、`.agent/state.json`（最终验收时切换当前模块）。不改其他已有文件，不涉及用户可见界面。

## Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| 字段值正文里恰好出现已知字段名开头的行，被误切成新字段 | 中 | 只认行首的已知字段名加冒号；用例覆盖「要点」正文里出现「来自：」的情况，并在 Spec 假设里已写明按约定块写法 |
| 宽松解析掩盖了写错的必填字段 | 中 | 必填字段只认字段表里的标准名，不做近义词匹配；「是否完全停住」只认「是」「否」 |
| 【用户答复】往返时用户原话里的换行、标点被改动 | 高 | 往返测试逐字比较，样例含多行原话、全角标点和「#」号 |
