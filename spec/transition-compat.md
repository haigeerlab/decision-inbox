# Spec: transition-compat

> 能力图模块 `transition-compat`（2026-10-18 用 add-module 插入，排在 hub-cutover-settings 之后）。来源：LIVE-SAAS 联合接入「插件补改」阶段，接入方案 D1、D8，用户决定 10。session-protocol 契约负责人 10-18 答复：兼容写法**不进契约**，由本插件做成过渡期适配，契约 v1.6 第 8 节写明了这一点。用户 2026-10-18 在本会话直接同意插入，并要求顺带把契约升到 v1.7。Spec 先交审。

## 目标

LIVE-SAAS 各线是逐条迁移的，前端线要等 module-crew 就绪才迁，可能要几天。迁移期间，新收件枢纽要和**还在用旧规则的会话**互相读得懂：

- 发给它们的答复，用它们认得的编号写法；
- 它们按旧规则写的取代、撤回，收件枢纽也认。

两种会话各管各的：已正式接入的会话一律用契约正式写法，不受影响。

## 现状（已核对代码与实际消息）

- **旧收件枢纽的实际写法**（10-18 旧收件枢纽发给前端线的消息，用 agent-relay 只读查看，前端线那边不会因此标成已读）：
  - 普通答复：`事项：#5990（hub 编号 372）`，`replyTo` 填 5990，即该线那条【等待用户】的邮箱号；后面接用户原话、选项原文、答复时间。
  - 多线答复：`事项：#5948（多线事项，发起方 live-saas-arch-review；hub 编号 370）`，后面接「适用于你的范围」。
  - 旧系统**没有【答复告知】**：负责人的事由负责人自己带编号和原话转交（SESSION-REGISTRY「指定负责人转交用户决定」）。
- 旧规则（m02 AGENTS.md 第 118–134 行）：【取代 #旧编号】和【撤回】「事项：#编号」里的编号，就是答复里「事项」后面那个号，也就是**该线自己那条消息的邮箱号**。新收件枢纽按 v1.7（`items.py` 的 `_not_owner`）会把这类消息整条退回。
- 新写法：`protocol.format_user_reply`、`format_multiline_replies`、`format_answer_notice`（`protocol.py` 第 387–430 行）写的是 `事项：#N（你的原消息 #M）`，N 是收件枢纽编号。
- 名册：只有 `onboard join` 能加开发线，而 join 一定会写约定块。没有「只登记」的入口。
- `leave` 只删约定块、记下 `left`，**不删名册条目**（`onboard.py` 第 595 行）。没写过规则文件的条目，leave 会报「没有记下规则文件」。
- 答复告知按名册里同线的开发线发（`hub.py` 的 `_notices`），**不跳过已经 leave 的条目**。
- 契约钉在 v1.5（`tests/test_contract.py` 的 `VERSION`）。v1.6 新增【负责人转交】，以及 user-reply 的「转自」写法；v1.7 只改条文。两版样例相同：解析 63、生成 6、跳过 26。
- 负责人约定块写的是「你仍要按原来的路线转交」，没有给出格式。

## 要做的

1. **只登记的条目**：新增 `onboard enroll <协作组> --relay-name … --short-name … --host … --line …`，只往名册里加一条开发线，不写任何规则文件。
   - 条目带 `legacyFormat: true`（「旧格式」），预览后经 `--confirm` 才写入。
   - 只用于开发线。负责人、总协调、收件枢纽要么正式接入，要么不进名册。
   - 这个会话以后用 `onboard join` 正式接入时，条目整个被替换，`legacyFormat` 随之消失，从此用正式写法。不需要另外的「切换」命令。
2. **发给旧格式会话的答复用旧写法**（收件人带 `legacyFormat`）：
   - 普通【用户答复】：首行写 `事项：#M（hub 编号 N）`。M 是这条答复所答的那条【等待用户】的邮箱号，N 是收件枢纽编号。其余字段照新写法，`replyTo` 照旧填 M。
   - 多线【用户答复】：写 `事项：#M（多线事项，发起方 <发起方身份名>；hub 编号 N）`。M 是发起方那条原消息的邮箱号，适用范围和原事项全文照新写法。
   - 【答复告知】**不发**给旧格式会话：旧系统没有这种消息，旧规则的线会把它当成待执行的答复。负责人仍按旧的「指定负责人转交」路线把决定交给这些线。
   - 收件枢纽发给发件人的退回说明（格式不合格、编号不对等），写编号时同时写邮箱号和 hub 编号，例如「#5990（hub 编号 372）」，让旧规则的线对得上。
3. **认旧格式会话写的编号**（发件人带 `legacyFormat`）：
   - 【取代 #X】：X 如果是这个发件人自己某个还没答复的事项的**邮箱号**，就当作那个事项。X 是收件枢纽编号时照常处理。两种都对不上时，照常按 not-owner 退回。
   - 【撤回】「事项：#X」：规则同上。
   - 「结束：#X」：本来就两种号都认，不变。
   - 正式接入的会话不享受这条，仍按 v1.7 只认收件枢纽编号。
4. **已退出的条目不再收消息**：
   - 名册条目在 `left` 里的，答复告知、多线答复都不再发给它。多线事项的「适用会话」里写了已退出的会话，按「不在名册里」退回给发起方。
   - `leave` 遇到没写过规则文件的条目（只登记的条目）：不报错，只记 `left`，并在输出里写明「这个会话没有约定块，只从收件范围里移除」。
5. **契约升到 v1.7**：
   - 测试样例换成 `tests/fixtures/session-protocol/v1.7`，从契约仓库 1e14a49 复制；不解析的样例加上 `user-reply/relay-*`（5 份）和 `owner-handoff/`（3 份），计数改为解析 63、生成 6、跳过 26。
   - README 的「消息协议」一节改为 v1.7。
6. **约定块写明【负责人转交】**：
   - 负责人约定块把「你仍要按原来的路线转交」改为：用【负责人转交】转交，字段是 `事项：#H（由<你的短名>抛出，原消息 #M）`、来自、用户原话、答复时间、转交范围（session-protocol v1.6）。
   - 开发线、总协调的约定块加一句：收到【负责人转交】时，核对三点：负责人已登记；如果收到过同一个 #H 的【答复告知】，用户原话要逐字一致；转交范围不超出原话。
   - 收件枢纽本身不解析【负责人转交】，它不会收到这种消息。
7. **文档与版本**：
   - README 加「迁移期：还没接入的会话」一节，写明 enroll、旧写法的范围、正式接入后自动换成新写法，并在升级一节写明 0.0.17 改了约定块。
   - 版本 0.0.17。所有约定块都改了（第 6 条），已接入的会话要重跑接入，doctor 会提示。

## 关键决策与取舍（请重点审）

1. **旧格式会话不发【答复告知】**：旧规则不认识这种消息，发了反而可能被误读成批准。代价是这些线在迁移期看不到负责人事项的答复，要等负责人转交。这和它们现在的做法一样。
2. **在输入方向也做兼容**：只改输出不够。旧规则的线写【取代】【撤回】时用的是自己的邮箱号，不兼容的话会被整条退回，又出一次 F1。只认「这个发件人自己还没答复的事项」，范围窄，不会认错。
3. **只登记的条目只能是开发线**：迁移期要过渡的只有开发线（前端线）。负责人、总协调在阶段 ⑤⑥ 就正式接入了。
4. **正式接入时自动换写法**：join 替换整个条目，不用多一个命令，也不会忘了切换。
5. **退出即停止收件**：这修的是 T18 指出的问题。名册条目照旧保留，历史可查。
6. **约定块改动和契约升级放在同一个模块**：它们都在改「各会话按哪份契约说话」，分成两个模块，各会话就要重跑两次接入。

## 验收标准

1. `onboard enroll`：预览不写任何东西；确认后名册里多一条带 `legacyFormat` 的开发线，不新建、不修改任何规则文件；用在非开发线角色上会报错；之后用 `onboard join` 正式接入，`legacyFormat` 消失。都有测试。
2. 发给旧格式会话的普通答复、多线答复，首行和旧收件枢纽的实际写法一致（以 `#5990（hub 编号 372）`、`#5948（多线事项，发起方 …；hub 编号 370）` 的形式断言）；发给正式会话的照旧。有测试。
3. 旧格式会话收不到【答复告知】；正式会话照常收到。有测试。
4. 旧格式会话用自己的邮箱号写【取代】【撤回】：能对应到自己还没答复的事项就生效；对应不上照常退回。正式会话用邮箱号写，照旧退回。退回说明里写双编号。有测试。
5. 已退出的条目收不到答复告知和多线答复；多线事项「适用会话」写了已退出的会话，会被退回；leave 只登记的条目不报错，规则文件都不变。有测试，覆盖联合测试 T18。
6. 契约测试跑 v1.7 样例：解析 63、生成 6、跳过 26，全部通过。
7. 负责人约定块写明【负责人转交】的字段；开发线、总协调约定块写明三项核对。有测试。
8. 原有测试全部通过；两份清单都是 0.0.17。
