# Spec: rehearsal-fixes

> 能力图模块 `rehearsal-fixes`（2026-10-18 预览插入，排在 crew-line-status 之后）。来源：LIVE-SAAS 联合演练批 1 的发现（`livesaas-integration/REHEARSAL-LOG.md`「批 1 小结」）。用户 2026-10-18 在本会话决定：四项改进合成一个模块，先写 Spec 交审；验收合并后冻结为 0.0.19，固定副本放 `~/Documents/haigeerlab/decision-inbox-release/v0.0.19`。批 2 等两个插件都冻结成固定副本后再开。

## 目标

修掉联合演练批 1 发现的四处不顺，让 LIVE-SAAS 切换那天少出意外：

1. doctor 不把「只登记」的条目报成问题；
2. leave 之前看得到这个会话名下还有哪些事没了结；
3. 【撤回】写错编号时，退回说明告诉发件人该写哪个号；
4. doctor 能直接看出 Claude 和 Codex 两边装的 decision-inbox 是不是同一版本。

## 现状（已核对代码与演练记录）

1. **只登记条目被报「未知」**：`doctor._conventions` 对名册里每个没退出的条目找规则文件。只登记（`legacyFormat`）条目本来就没有规则文件，于是报「？ 约定块：旧格式：接入记录里没有它的规则文件」。批 1 实测。
2. **leave 不提示没了结的事**：`onboard._leave` 和 `_leave_enrolled` 的预览只说规则文件怎么改。批 1 第 ⑤ 步实测：旧格式条目名下有一项没答的 #11，预览只写「只从收件范围里移除」；确认后 #11 仍挂在主视图里。这个会话开着的等待单也一样不提。
3. **【撤回】的退回说明不点明事项号**：`items._receive_withdraw` 调 `_not_owner(msg.item)` 时没传 `doc`、`sender`，所以正式会话把自己的邮箱号写进【撤回】时，只得到「#N 不存在，或不是你抛出的事项」。【取代】已经会点明对应事项号（p0-field-fixes），但那句提示的写法专指【取代】。契约 v1.9 写明【撤回】只认事项号，是否点明由插件决定（契约负责人建议点明）。
4. **两边版本可能不一致**：批 0 实测，Codex 侧缓存停在 0.0.15，重开 Codex 会话时，它的启动钩子把转发脚本切到 0.0.15，Codex 会话的停止钩子也跑旧版。doctor 只能从「转发脚本」一项间接看出来。两边的安装记录都是文件，可以只读核对：
   - Claude：`~/.claude/plugins/installed_plugins.json`；目录型市场按源目录取版本（`deps.find` 已经这样做）。
   - Codex：`~/.codex/config.toml` 里有 `[plugins."decision-inbox@<市场>"]`，`enabled = true`；装好的副本在 `~/.codex/plugins/cache/<市场>/decision-inbox/<版本>/`。
5. 仓库没有 `.gitignore`，在仓库目录里运行命令会留下 `decision_inbox/__pycache__/`，显示成「未提交改动」。

## 要做的

1. **doctor 不再把只登记条目报成未知**：带 `legacyFormat` 的条目，这一项报 ok，写「只登记，不写约定块（迁移期旧格式会话）」。
2. **leave 预览列出没了结的事**（正式条目和只登记条目都适用）：
   - 列出这个会话抛出的、还没结束的事项（编号、要你决定的首行），以及它作为等待方、还开着的等待单（编号、在等谁）；
   - 写明 leave 之后会怎样：这些事项继续留在主视图里，收件枢纽不再给它发任何消息；
   - 写明处理办法：
     - 事项：leave 之前由它自己发【撤回】，或你在收件枢纽答复后由负责人另行转交；
     - 等待单：你在收件枢纽说「关掉 #编号」。
   - 只提示，不拦：确认后照常 leave。没有这类事时，预览不多写。
3. **【撤回】编号写成自己邮箱号时点明事项号**：
   - `_receive_withdraw` 把 `doc`、`sender` 传给 `_not_owner`。
   - `_not_owner` 增加消息类型参数，【撤回】时提示「#N 是邮箱号，对应事项 #M；改写「事项：#M」重发【撤回】」。【取代】的现有提示不变。
   - 退回代码仍是 not-owner，契约行为不变。旧格式会话本来就认邮箱号（transition-compat），不受影响。
4. **doctor 核对两边版本**：新增一项「Claude、Codex 两边的版本」。
   - 只读文件：本次运行的代码版本、Claude 装的版本、Codex 装的版本（Codex 配置里启用了本插件时，取缓存目录里的版本；目录里有几个版本就全部列出）。
   - 判定：
     - 两边都装了且版本一致：ok；
     - 版本不一致，或 Codex 缓存里有多个版本：异常，来源「Claude Code／Codex 安装」，并给出重装命令；
     - 只装了一边：ok，写明「Codex 没装」或「Claude 没装」。
   - 重装命令为 `codex plugin remove decision-inbox@<市场>`，再 `codex plugin add decision-inbox@<市场>`，或者 Claude 侧对应的更新方式。
5. **`.gitignore` 加 `__pycache__/`**。
6. **文档与版本**：
   - README「排查」表加「两边版本不一致」一行，leave 一节写明会列出没了结的事；
   - 新增「固定副本安装」一节，写明怎样从固定副本安装、两边怎样指向同一个副本（给演练和 LIVE-SAAS 接入用）；
   - 版本升到 0.0.19；约定块不变，已接入的会话不用重跑。

## 关键决策与取舍（请重点审）

1. **leave 只提示、不拦**：切换那天，fe 名下的事怎么处理，你可能有不同选择：撤回、留着，或者转给协调会话。插件替你拦下来反而碍事；列清楚，并写明各自怎么处理就够了。
2. **版本核对只读文件，不运行 `codex plugin list`**：doctor 一贯只读文件（只有 module-crew 出口是你批准的例外）。Codex 的缓存目录和配置文件足以判断。代价是：如果 Codex 将来改了目录结构，这一项会报「读不到」，而不会误报一致。
3. **Codex 缓存里有多个版本算异常**：说明有旧副本残留，Codex 加载哪一个说不准。这正是批 0 遇到的情况。
4. **【撤回】点明事项号，但不替它改写**：契约规定【撤回】只认事项号；收件枢纽不去猜，只告诉发件人该写哪个号。
5. **固定副本的打标签、建副本、改安装放在合并之后，单独请你批准**：这几步改的是你本机的安装，而且依赖合并后的提交。

## 验收标准

1. doctor：只登记条目这一项为 ok，写「只登记，不写约定块」；正式条目的约定块检查不变。有测试。

3. 【撤回】：正式会话写自己某个没结束事项的邮箱号，被退回，说明里点明「对应事项 #M」，并给出【撤回】的改写；写不存在的号，说明照旧；【取代】的提示不变；旧格式会话写邮箱号照旧生效。有测试。
4. doctor 版本一项：
   - 两边一致：ok；
   - 不一致：异常，并给出命令；

   - Codex 没装或没启用、Claude 没装：ok 并写明；
   - Codex 配置读不到：未知。

   全部用临时目录测试，不依赖本机安装。
