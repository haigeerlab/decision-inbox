# Spec: join-deny-label

> 能力图模块 `join-deny-label`（2026-10-19 用户确认插入，排在最后，不插队）。来源：父会话「Decision-inbox 插件第 3 阶段能力图」报告的 0.0.28 缺陷（用 0.0.28 给 di-p0 的 main 审查与 rh2-coord 跑 `join --confirm` 时发现）。插入时的假设 1–5 用户 2026-10-19 确认。

## 目标

接入预览和写入回执里，每条权限规则的标签与它实际写进的数组一致：放行写「放行」，先问写「先问」，禁止写「禁止」。用户看着预览批准的，就是实际写进去的。

## 现状（已核对代码）

- `decision_inbox/__main__.py` 第 504、506 行：`'放行' if kind == 'allow' else '先问'`——只分两种。permission-closeout 新增的 `ALWAYS_DENY`（全局安装 11 条、管道到 shell 5 条，共 16 条）以 `("deny", 规则)` 进入 `out.permissions`，于是被打印成「要加 先问」「已加 先问」。
- 写入（`onboard._merge_rules`）按种类写进对应数组，16 条都在 `deny` 里，符合 permission-closeout Spec 第 1 节（本意是禁止）。
- permission-closeout 的测试只核对写入的数组，没核对打印的标签。
- 影响：父会话已用 0.0.28 给 di-p0 的 main 审查（`di-p0/owner`）与 rh2-coord（`crew-rehearsal`）跑过 `join --confirm`，用户看到的是「先问」，实际写进的是「禁止」，比显示的更严。

## 要做的

1. 标签按种类：`allow`→「放行」、`ask`→「先问」、`deny`→「禁止」；「要加／已加」与「要删／已删」两处都用同一张对照表。
2. 遇到不认识的种类时原样打出种类名，不猜（防止以后再加种类时又被归到别的标签下）。
3. 测试：用命令行跑一次预览、一次确认，对每一条打印出来的规则，核对标签与它在 `settings.local.json` 里所在的数组一致；全局安装与管道到 shell 的规则显示「禁止」。

## 关键决策与取舍

1. **只改标签，不改写入**（假设 1）：写入符合已批准的 Spec；改写入等于推翻用户批准的 permission-closeout。
2. **已写进 di-p0 的规则不动**（假设 5）：它们本来就是对的；README 和接入预览已说明全局安装与管道到 shell 是禁止。

## 范围

做：`decision_inbox/__main__.py`（标签）；`tests/test_onboard.py`（标签与数组一致的测试）。

不做：不改写入、不改规则清单、不动 di-p0 现有配置；版本号另开 PR 发 0.0.29，冻结和安装切换另请用户批准（假设 4）。

## 验收标准

1. 预览里 16 条禁止规则显示「要加 禁止」，确认后显示「已加 禁止」；放行、先问照旧。
2. 打印出的每条规则，标签与它在 `settings.local.json` 里的数组一致（测试逐条核对）。
3. 「要删」那一行照旧显示「先问」（旧版写的两条先问规则）。
4. 全量测试通过，旧称扫描通过。
