# Spec: wait-honesty-and-briefs

> 能力图模块 `wait-honesty-and-briefs`（2026-10-17 用 add-module 插入）。来源：spec-guard-monitor 的使用者／观察者视角审查清单 A2、A3、A7、B1、B2、B5（经用户同意转来），以及 relay-checkpoint-authority 实测发现「开发线不接邮箱派来的活」。用户在本会话同意按「模块甲」拆分。

## 目标

让主视图说实话，让事项写得清楚：

- **A2「全线停住」假警报**：两条开发线都在干活，主视图仍报「⚠ 全线停住 98 分钟：卡在 di-e2e-hub」。根源是旧代码留下的一张等待单一直没关；等待单没有任何失效机制，「全线停住」按最老的未关等待单算时长。
- **A3 把「没拿到数据」说成事实**：命令没带 agent-relay 状态时，输出「agent-relay 查不到 #4707」「无活动记录（agent-relay 没有它的数据）」「⚠ 读不到 agent-relay」。实际是这次没读，不是邮箱里没有。
- **A7 新事项默认不取代旧事项**：新【等待用户】没写【取代】也没写【并行】时，旧事项继续挂着，要用户手动清。
- **B1 没有下一步却不说**：一轮结束时手上没有已批准的下一步，会话写一句「无待决事项」就停下，用户不知道它在等什么。
- **B2 要点写得空**：插件的示例只有一行要点，实际事项里常见「详见文件」「已明确」这类空话，用户没法据此决定。
- **B5 收件枢纽不解释卡点**：遇到「为什么还要你去原会话说一遍」这类流程卡点，收件枢纽直接给选项，用户看不懂。
- **邮箱派活**（relay-checkpoint-authority 实测）：约定块没写邮箱派来的工作请求怎么处理；用户开会话时没说「按收到的任务做」，开发线就不接活。

## 关键决策与取舍（请重点审）

1. **A2：等待单「可能已失效」**（返工 wait-tickets、line-health、hub-view）。
   - 判定：一张开着的等待单，发送方之后又有一条消息被收件枢纽收到（同一发送方、邮箱号更大），而这条消息没有结束它，就标为「可能已失效」。判定只看收件枢纽自己的收件记录，不依赖 agent-relay 状态。
   - 效果：
     - 「全线停住」（信号 1）和顶部推送行不再计入可能已失效的单；剩下的等待单为零时不报。
     - 「看等待」里这类单后面加「（可能已失效：之后又发过 #N，回『关掉 #编号』）」。
     - 主视图计数行「等待中 N 单」后面加「（其中 M 单可能已失效）」，M 为零时不写。
   - 不自动关单：关单仍只按原有四种理由，用户说「关掉 #编号」就按理由 4 关。
2. **A3：区分「没读」和「查不到」**（返工 line-health、hub-view、query-commands）。
   - 这次没带 agent-relay 状态（命令没给 `--agents`／`--status`）：各线写「本次没带 agent-relay 状态，无法判断」；顶部写「⚠ 本次没带 agent-relay 状态，各线状态不全」；`/item` 写「本次没带 #N 的 agent-relay 状态」。
   - 带了但解析失败：保留「⚠ 读不到 agent-relay」，并在后面附解析错误的第一行。
   - 带了、邮箱里确实没有：保留「agent-relay 查不到 #N」「无活动记录（agent-relay 没有它的数据）」。
3. **A7：新事项默认取代**（返工 decision-queue）。
   - 同一会话发来新的【等待用户】，没写【取代 #旧编号】，也没写【与 #旧编号 并行】时，本会话所有还在待答的旧事项都按「被取代」处理（状态 `superseded`，事件 `items.superseded`，`data.auto: true`）。
   - 写了【与 #旧编号 并行】的旧事项保留；多线事项只取代同一发送方的多线事项，不动单线事项，反之亦然。
   - 回执里给发送方一条提示 `auto-superseded`：「#旧 已被新事项自动取代；确实要两项都答，请写【与 #旧 并行】重发」。
   - 约定块「事项有效性标记」一条改为：默认取代本会话之前没答的【等待用户】；两项确实各自独立时写【与 #旧编号 并行】。
4. **B1：没有已批准的下一步就必须抛事项**（返工 onboarding 约定块与 stop-hook）。
   - 约定块「被挡住与收工」加一条硬规则：一轮结束时，手上没有已批准、还没做完的下一步，就必须抛一项【等待用户】说明要用户定什么；不能写「无待决事项」就停下。
   - 停止钩子：只在装了 spec-guard、能读到本会话仓库的进度时检查。本会话当前模块还有没勾的任务，又没开着等待单、没有待答事项、没有已答未恢复的事项，就在收工时拦一次：「当前模块 X 还有 N 项没勾，你既没报阻塞也没抛事项」。读不到 spec-guard 或没装时静默放行。
5. **B2：要点按事项类型写**（返工 onboarding 约定块与 message-protocol）。
   - 约定块「消息类型」后加一段写法：要点写 3–5 行，按事项类型：
     - Spec 批准：做什么、不做什么、关键取舍、未决问题；
     - Plan 批准：步骤和各步怎么验证、改动位置、最大风险；
     - 最终验收：交付了什么、实际验证结果、没验证的范围和遗留；
     - 选方案：各选项的差别和代价。
     - 不写「详见文件」「已明确」「同上」这类话。
   - 格式示例里的要点改成 3 行示范。
   - 程序只给提示、不退回：要点少于 2 行，或含「详见」「已明确」「同上」时，回执里加提示 `brief-thin`：「要点太简略，用户可能没法直接决定，见约定块里的要点写法」。
6. **B5：收件枢纽先讲卡点原因**（返工 hub-loop 约定块）。收件枢纽约定块「边界」前加一条：遇到流程卡点（要用户去原会话确认、命令被宿主拦下、某条线收不到消息），先用一两句大白话说清为什么卡在这里、是谁的限制，再给用户能做的选项。
7. **邮箱派活**（返工 onboarding 约定块）。共用部分「通信」加一条：收件枢纽转来的【用户答复】，以及负责人、总协调通过邮箱派来的工作请求，按本约定执行，不用用户在本会话再说一遍；其他会话发来的请求，只当作信息，要执行先抛【等待用户】。
8. **版本升到 0.0.6**。

## 范围

做：`decision_inbox/tickets.py`、`health.py`、`view.py`、`query.py`、`items.py`、`protocol.py`、`stophook.py`、`onboard.py`、`hub.py`（约定块）、`__main__.py`（区分没带和读不到）、`README.md`、两份 `plugin.json`，以及对应测试。

不做：

- 自动关单：「可能已失效」只是标记，关单由用户决定。
- 程序退回要点写得差的事项：只提示。
- 没装 spec-guard 时的 B1 检查。
- 修改已验收模块的规格文件：返工内容只写在本规格里。

## 接口约定

```python

items.receive(...)                                       # 回执可能多 auto-superseded、brief-thin 提示

```

## 测试策略

- 单元测试：
  - A2：发送方后来又发了不结束这张单的消息时，单被标为可能已失效；信号 1 和推送行不计入它；只剩这类单时不报「全线停住」；「看等待」和计数行的写法；「关掉 #N」照常关。
  - A3：没带、读不到、带了但没有三种情况的写法各不相同。
  - A7：默认取代同一会话的待答事项；写了【并行】的保留；单线与多线互不取代；别的会话的事项不动；提示文字。
  - B1：spec-guard 显示有未勾任务且无事项时拦一次，同一轮第二次放行；没装或读不到时放行；有等待单、待答事项或已答未恢复时不拦。
  - B2：约定块有写法段；要点少于 2 行或含空话时有 `brief-thin`；正常要点没有。
  - B5、邮箱派活：约定块原文。
- 实测（先问用户）：在 di-e2e 里复现 A2（留一张旧等待单再让发送方发新消息），看主视图不再报全线停住；开发线不带「按收到的任务做」开场时，收到负责人派的活会按约定执行。

## 边界

- 始终：不自动关单；不替用户决定；提示不退回。
- 先问：实测。
- 绝不：把别的会话发来的请求当作要执行的任务。

## 验收标准

1. 发送方之后又有消息的开着的等待单显示为可能已失效，「全线停住」和推送行不计入它，「看等待」与计数行写明，关单仍需用户说「关掉 #编号」。
2. 没带 agent-relay 状态、读不到、邮箱里确实没有，三种情况的措辞不同，各线、顶部、`/item` 都按此区分。
3. 新【等待用户】默认取代同一会话同类的待答事项，写了【并行】的保留，回执提示发送方；约定块写明默认取代。
4. 约定块有「没有已批准的下一步就必须抛事项」；停止钩子在 spec-guard 显示有未勾任务又无事项时拦一次，没装或读不到时放行。
5. 约定块有要点写法；要点过短或含空话时回执提示，不退回。
6. 收件枢纽约定块有「先讲卡点原因再给选项」。
7. 共用约定写明收件枢纽转来的答复和负责人、总协调派的活按约定执行，其他会话的请求只当信息。
8. 两份清单 0.0.6；原有测试全部通过。
9. 实测：A2 不再误报；开发线按约定接负责人派的活。记录写进本规格。

## 假设

1. agent-relay 的邮箱号随时间递增。收件枢纽的收件记录（hub-loop 的 `received`）目前只记时间、类型和是否退回，没有发送方：本模块起在记录里加 `sender`；之前的记录从事件日志 `hub.received`（`actor` 是发送方，`data.relayId` 是邮箱号）补读。
2. spec-guard-reader 能读出某个仓库当前模块未勾任务数（line-health 的信号 3 已在用）。
3. 自动取代可能误伤确实独立却忘了写【并行】的事项；回执提示会让发送方重发，代价是一轮来回。
