# Spec: wait-tickets

> 能力图模块 `wait-tickets`。需求来源：`docs/requirements-record.md` 第 4.1 节（结束写法）、第 4.5 节、第 3.3.2 节（按四种理由关单、超时提醒）、第 6.1 节第 5 条。

## 目标

管理等待单。每条还没结束的【等待其他会话】都是一张等待单，记着哪个会话在等谁、等什么、从什么时候开始等。

本模块负责：
- 按需求第 4.5 节，**只按四种理由**关单；
- 关闭的单不删，移进「今天已关闭」；
- 给还开着的单加提醒：已等多久、可能卡住、对方离线。

实验里有一张等待单挂了 76 分钟没人关，这个模块就是为了不再发生这种事。

本模块只记录和标记：不联系任何会话、不催、不替谁关单，四种理由之外一律不关。

## 范围

**范围内**

- 收到【等待其他会话】时登记等待单，编号用 group-store 的共用编号序列。
- 四种关单理由，每种都写明理由和依据：
  1. **对方明说结束**：等待方后来发的【已恢复】，结束行写了这张单的编号。
  2. **被取代**：同一会话又发了新的【等待其他会话】或【等待用户】，结束行写了这张单的编号。
  3. **所等的事已发生，有收件枢纽亲手经办的证据**：只限在等用户答复的单，并且枢纽已经转发了对应答复。依据写「已转发 #答复的消息编号」。
  4. **用户说「关掉 #编号」**：可以带原因，没写原因记「用户关闭」。
- 给开着的单加标记：
  - 已等 15 分钟及以上：「⚠ 已等 N 分钟」；
  - 已等 60 分钟及以上：「可能卡住」，并附一句提示「X 在等 Y 的什么，请看一下 Y 是否已完成却没通知 X」；
  - 被等方离线或连不上：立即标「⚠ 对方离线」，并提示「X 离线，有 N 条消息送不进去，最早一条是 HH:MM 发的」。
- 提供三样数据：今天已关闭的单、开着的单数、今天已关的单数，供主视图最后一行使用（需求第 6.1 节第 5 条）。

**范围外**

- 联系、催促、叫醒任何会话：归 patrol。
- 按信号判断卡住，比如全线互等、孤儿等待：归 line-health。本模块的「可能卡住」只是需求第 4.5 节的固定兜底提醒。
- 显示格式：归 hub-view。
- 【等待用户】事项本身：归 decision-queue。

## 关键决策与取舍（请重点审）

1. **已等多久按消息发出时间算，不按收到或读到的时间**（需求第 4.5 节）。发出时间取 agent-relay 记录的消息创建时间，由调用方随消息一起传入。
2. **结束行只对自己的单生效。** 结束行里写的编号，如果是别的会话的等待单，不关，并给出提示 `not-own-ticket`。如果编号是一个【等待用户】事项，本模块忽略它，那归 decision-queue 处理。
3. **「被取代」只认显式的结束行。** 同一会话就同一件事发了新的等待，但没在结束行写旧编号的，不算取代，旧单保持开着。「是不是同一件事」需要读懂内容，本模块不靠猜。旧单挂久了会自然走到「可能卡住」的提醒。
4. **理由 3 怎么识别「在等用户答复」**：「在等谁」写「用户」或「收件枢纽」，并且「等什么」里写了 `#N`，N 是这个会话自己抛的【等待用户】事项。这个事项已转达、并且已经记下发送编号时，才能按理由 3 关单。依据写「已转发 #〈答复的 agent-relay 消息编号〉」，编号取自 decision-queue 记下的发送记录。
5. **「在等谁」对不上名册时照样登记**，只是不检查对方在不在线，并给提示 `unknown-target`。等待单是给人看的提醒，不该因为名字写得不规范就丢掉。
6. **「今天」按本机时区的日期算。** 「今天已关闭」只是显示上的分组，文件永久保留（第 12 节第 11 项已定）。
7. **15／60 分钟是需求第 4.5 节原文给的固定数字**，写成模块常量，不做配置项。巡视用的按信号检测和门槛（第 12 节第 3 项），留到 line-health 再定。

## 状态与数据

快照放在 group-store 的领域 `tickets`。每张单记这些内容：编号、等待方的身份名、「在等谁」的原文、能对上名册时对应的身份名、等什么、发出时间、agent-relay 消息编号、状态（`open` 或 `closed`），以及关单信息（理由 1～4、依据、时间）。

事件类型：`tickets.opened`、`tickets.closed`。

## 接口约定

```python
from decision_inbox import tickets

r = tickets.receive(g, text, sender="fe-codex", relay_id=310, sent_at="2026-10-16T05:01:00Z")
r.handled     # 【等待其他会话】【已恢复】为 True；【等待用户】也为 True（只处理它的结束行）；其他为 False
r.opened      # 新登记的等待单编号，或 None
r.closed      # 这次按理由 1／2 关掉的编号
r.hints       # not-own-ticket、unknown-target，以及 message-protocol 的提示
r.problems    # 【等待其他会话】不合格时 message-protocol 的问题；不合格的不登记

tickets.close_answered(g, at="...")                    # 按理由 3 扫一遍；返回关掉的编号
tickets.close_by_user(g, ticket=31, reason=None, at="...")   # 理由 4；单不存在或已关闭时抛 ValueError

views = tickets.open_tickets(g, now="...", relay=agents_snapshot)   # relay 可为 None：那就不做离线判断
views[0].no, views[0].waiter, views[0].target, views[0].what, views[0].minutes
views[0].marks     # ("waited",)、("waited", "maybe-stuck")、("offline",) 等
views[0].notes     # 每个标记对应的一句中文提示

tickets.closed_on(g, day="2026-10-16")   # 那一天（本机时区）关闭的单，带理由与依据
tickets.counts(g, day="2026-10-16")      # {"open": N, "closed_today": N}
```

- `relay` 参数是 relay-reader 的 `AgentsSnapshot`。被等方的 `presence` 为 `offline` 或 `unreachable`，就标 `offline`；`waiting_count` 和 `waiting_oldest_at` 用来写提示。
- 本模块不提供四种理由以外的关单接口。

## 依赖

- 本插件模块：group-store、message-protocol、relay-reader（在线状态与积压数）、decision-queue（理由 3 所需的事项状态和发送记录）。
- 外部组件：无直接调用。在线状态和积压数来自 agent-relay 的 `bridge_agents`，由会话转交原文、经 relay-reader 解析后传入。

## 边界

- **始终**：只按四种理由关单，写明理由和依据；已等时间按发出时间算；关闭的单保留。
- **先问**：增加关单理由；修改 15／60 分钟；让本模块联系任何会话。
- **绝不**：因为看起来过时、等太久、对方在忙就关单；替别的会话判断它的交付；删除等待单。

## 验收标准

1. 合格的【等待其他会话】：登记为开着的单，编号来自共用序列，记下等待方、在等谁、等什么、发出时间、消息编号；有事件 `tickets.opened`。不合格的（例如缺「等什么」）：不登记，`problems` 给出原因。
2. 理由 1：等待方的【已恢复】结束行写了 `#31`，31 号单关闭，理由 1，依据记下这条【已恢复】的消息编号。别的会话的【已恢复】写 `#31`：不关，提示 `not-own-ticket`。
3. 理由 2：同一会话新发的【等待其他会话】或【等待用户】，结束行写 `#31`：31 号单关闭，理由 2，依据是新消息的编号。结束行写「无」：旧单保持开着。
4. 理由 3：等待单「在等谁：用户」「等什么：#12 的答复」；12 号事项已转达并记下发送编号 2950 后，`close_answered` 关掉它，依据「已转发 #2950」。事项还没转达时不关；「在等谁」是别的会话时不关。
5. 理由 4：`close_by_user(ticket=31)` 关闭，原因为「用户关闭」；带了原因就记原因。单不存在或已关闭时抛 `ValueError`。
6. 标记：发出后 14 分钟没有标记；15 分钟是 `waited`，提示「⚠ 已等 15 分钟」；60 分钟是 `waited` 加 `maybe-stuck`，提示含「X 在等 Y 的什么」。时间按发出时间算，与登记时间无关。
7. 离线：被等方 `presence` 为 `offline` 且有 3 条积压时，不论等了多久都立即标 `offline`；提示含「离线」「3 条」，以及最早一条的本机时间 HH:MM。不传 `relay` 时不出现 `offline`。
8. 「在等谁」对不上名册：照样登记，提示 `unknown-target`，不做离线判断。
9. `closed_on` 只返回本机时区当天关闭的单；`counts` 的 `open` 和 `closed_today` 正确。已关闭的单仍在快照和事件日志里。
10. 所有变化都写入 `tickets` 快照和事件日志，`store show` 的一致性检查为正常。

## 假设

1. 收件枢纽会话把收到的【等待其他会话】【已恢复】【等待用户】原文，连同 agent-relay 的发件人、消息编号、消息创建时间，都交给本模块。【等待用户】同时也交给 decision-queue。
2. 「在等谁」写的是名册里的短名，或者「用户」「收件枢纽」；这些写法在 onboarding 的约定块里统一。
