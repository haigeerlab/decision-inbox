# Spec: review-registry

> 能力图模块 `review-registry`。需求来源：`docs/requirements-record.md` 第 4.3 节、第 5.2 节、第 8.1 节信号 7、第 3.1～3.2 节，第 12 节第 8 项。

## 目标

管理三件事：
1. **审查者登记**：哪个会话有审查者、审查者是谁、审哪几类节点。登记的增改要经用户批准。
2. **审查状态行的显示**：把【等待用户】里的「架构审查：…」按需求第 4.3 节的规则换成收件枢纽上的短标签。
3. **审查轮数**：按负责人抄送来的【审查结论】，统计同一审查来回了几轮，供 line-health 的信号 7「反复返工」使用。

使用方：hub-view、map-view（显示审查标签和审查列）、decision-queue（收单时取标签）、line-health（轮数）、onboarding（接入时写入登记）。

## 已定事项（用户 2026-10-16 确认）

1. **第 12 节第 8 项：不加第五类节点。** 第一版的节点固定为实验里的四类：Spec、Plan、接口提案、最终验收（含提交范围）。风险接受／例外仍作为负责人提案直接抛给用户批，不增加一轮架构审查。
2. **审查轮数的来源：负责人静默抄送。** 负责人每出一次审查结论，就静默发一条【审查结论】给收件枢纽（不唤醒）；轮数等于同一审查编号收到的结论条数。消息格式由 message-protocol 定义，本次一并修订。

## 范围

**范围内**

- 登记、修改、撤销审查者，每次都记下生效时间和用户批准的依据。
- 按生效时间判断某条事项是否适用审查：事项收到时登记已生效才适用，也就是需求第 4.3 节说的「新事项适用」。
- 按需求第 4.3 节的显示规则生成审查标签。
- 记录【审查结论】，按审查编号统计轮数，给出已结束和进行中审查的轮数。

**范围外**

- 判断该不该审、审得对不对（需求第 11.3 节：插件不审查）。
- 「已抛出但未执行的同节点事项先补审再执行」：这是对各会话的要求，写进 onboarding 的约定块。本模块不跟踪事项属于哪个节点，因为【等待用户】里没有节点字段。
- 判断轮数算不算多：比较门槛属于 line-health，涉及第 12 节第 3 项。
- 核实用户批准的真伪：本模块只记录调用方给的批准依据；只有用户在收件枢纽批准后，调用方（decision-queue、onboarding）才会调用。

## 关键决策与取舍（请重点审）

1. **登记按会话记，保留历史。** 每次登记、修改、撤销都追加一条带生效时间的记录，不覆盖旧的。判断某条事项适用哪份登记时，取事项收到那一刻已生效的那份。这样新登记不会追溯改变已经显示过的旧事项（需求第 4.3 节「已执行的历史批准不追溯撤销」）。
2. **审查者必须是名册里的负责人**（`role=owner`），送审方必须是开发线或总协调。需求第 3.1 节写的是「负责人兼任审查者」。
3. **显示只看登记和那一行，不推断**（需求第 4.3 节第 1～3 条）：
   - 会话没登记审查者：一律显示「不需审：本会话无审查者」，即使正文写了审查行也不看。
   - 登记了审查者，审查行是五种写法之一：显示对应的短标签。
   - 登记了审查者，审查行缺失或认不出：显示「⚠ 未标审查」，并原样摘出正文里提到「审查」的行，不替它判断算不算审过。
   - 「审查中，请勿先批」要醒目标出，但不扣住答复。扣不扣、转不转是 decision-queue 的事，按原话转。
4. **轮数只认登记的审查者发来的结论。** 【审查结论】的发件人不是送审方登记的审查者，或者节点不在登记范围内：不计入轮数，返回问题代码，由调用方提示用户。这样别的会话发不了假结论来刷轮数。
5. **一个审查编号在收到「通过」或「通过，附建议 N 条」后即结束**；结束后再收到同一编号的结论，记为新一轮并重新打开，同时给出提示。审查编号由负责人起名，本模块不分配。

## 接口约定

```python
from decision_inbox import reviews

reviews.register(g, session="fe-codex", reviewer="fe-owner",
                 nodes=("spec", "plan", "interface", "final"),
                 approval_item=12, approval_note="用户原话：12 A",
                 at=None)    # 修改也用它：整份替换并记新的生效时间；at 是生效时间，不传取当前时间
reviews.unregister(g, session="fe-codex", approval_item=15, approval_note="...", at=None)
# 登记不合格（角色、节点、批准依据为空、撤销时没有在用的登记）抛 reviews.InvalidRegistration，什么都不写
reviews.registration_at(g, "fe-codex", at="2026-10-16T14:05:00+08:00")  # Registration 或 None

label = reviews.display_label(g, session="fe-codex", message=msg, received_at="...")
label.text        # 「已审：通过」「⚠ 未标审查」……
label.warn        # 是否带 ⚠
label.highlight   # 「审查中，请勿先批」时为 True
label.ref         # 审查编号，没有为 None
label.mentions    # ⚠ 未标审查时，正文里提到「审查」的原行

result = reviews.record_conclusion(g, message=conclusion_msg, sender="fe-owner", at="...")
result.recorded   # 是否计入轮数
result.problems   # 不计入的原因（下方问题代码），计入时为空
result.hints      # 计入但要提示用户的情况：重新打开已结束的审查时为 reopened
stats = reviews.round_stats(g)
stats.closed      # ((review_ref, submitter, node, rounds), ...)，已结束的审查
stats.open        # 同样的元组，进行中的审查
```

- 节点代码：`spec`（Spec）、`plan`（Plan）、`interface`（接口提案）、`final`（最终验收＋提交范围）。四类之外的一律拒绝。
- 显示文字与需求第 4.3 节的表逐字一致：

  | 审查行 | 显示 |
  |---|---|
  | 通过 | 已审：通过 |
  | 通过，附建议N条 | 已审：通过，附建议N条 |
  | 进行中，请勿先批 | 审查中，请勿先批（`highlight`） |
  | 不适用（不属于审查节点） | 不需审：不属于审查节点 |
  | 用户豁免 | 用户豁免 |
  | 缺失或认不出 | ⚠ 未标审查（`warn`，附 `mentions`） |
  | 会话没登记审查者 | 不需审：本会话无审查者 |

- 问题代码（只增不改）：
  - `not-registered-reviewer`：发件人不是送审方登记的审查者；
  - `node-not-registered`：节点不在登记范围内；
  - `bad-conclusion`：消息本身不合格，具体原因见 message-protocol 给出的问题。
- 提示代码（只增不改）：`reopened`，已结束的审查又收到结论，已重新打开并计入一轮。
- 状态存放：group-store 的领域 `reviews`，快照 `state/reviews.json`，事件类型 `reviews.registered`、`reviews.unregistered`、`reviews.conclusion`。

## 依赖

- 本插件模块：group-store（状态、事件、名册）、message-protocol（审查状态行、【审查结论】的解析）。
- 外部组件：无。【审查结论】经 agent-relay 送到收件枢纽，但由收件枢纽会话接收后交给本模块，本模块不调用 agent-relay。

## 测试策略

- 用 group-store 的临时目录建一个协作组，名册里放开发线、负责人、总协调各一。
- 显示规则逐行覆盖上表；登记时间前后各一条事项，验证「新事项适用、旧事项不追溯」。
- 轮数用几条构造的【审查结论】覆盖：多轮后通过、冒名、节点不符、结束后重开。

## 边界

- **始终**：显示文字与需求第 4.3 节逐字一致；登记变更必须带批准依据；保留登记历史。
- **先问**：增加节点类型；改变显示文字；把轮数比较门槛放进本模块。
- **绝不**：判断审得对不对；扣住或改写答复；替任何会话补审查结论。

## 验收标准

1. 登记 fe-codex 的审查者为 fe-owner、节点四类：`registration_at` 在生效时间之后返回这份登记，之前返回 None；登记事件里带批准依据。
2. 审查者不是名册里的负责人、送审方是收件枢纽、节点含第五类、批准依据为空：都被拒绝，状态不变。
3. 已登记的会话，审查行为五种写法时，`display_label` 的文字逐字等于上表；「进行中，请勿先批」的 `highlight` 为真。
4. 已登记的会话，审查行缺失或认不出：文字为「⚠ 未标审查」，`warn` 为真，`mentions` 原样包含正文里提到「审查」的行。
5. 没登记的会话，不管审查行写了什么：文字都是「不需审：本会话无审查者」。
6. 登记生效前收到的事项显示「不需审：本会话无审查者」，生效后收到的按规则显示；撤销登记后的新事项回到「无审查者」，撤销前的旧事项结果不变。
7. 同一审查编号先后收到「有须修改项」「有须修改项」「通过」：`round_stats` 里该审查已结束、轮数为 3。
8. 发件人不是登记的审查者：返回 `not-registered-reviewer`，不计轮数；节点不在登记范围：返回 `node-not-registered`；消息不合格：返回 `bad-conclusion`。
9. 已结束的审查再收到同编号结论：重新打开，轮数加 1，并给出提示。
10. 所有变更都同时写入 `reviews` 快照和事件日志，`store show` 的一致性检查为正常。

## 假设

1. 审查编号由负责人起名，在同一协作组内不重复。重复使用视为同一审查，按关键决策 5 处理。
2. 负责人会照约定块静默抄送【审查结论】；漏抄时轮数偏少。漏抄本身不在本模块检测。
