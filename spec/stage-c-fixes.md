# Spec: stage-c-fixes

> 能力图模块 `stage-c-fixes`（2026-10-20 用户确认插入，排在 wait-closed-item 之后）。来源：接入协调转来的 R22（`livesaas-integration/REQ-R22-STAGE-C-FIXES.md` 第一、三节；决定 71，用户 2026-10-20 同意补派），证据见 `STAGE-C-REPORT.md` 第四、九节。用户 2026-10-20 定：三条合成一个模块（D1 B），巡视提醒走本机 launchd 定时检查（D2 A），一起发 0.0.31；冻结期间不装到 di-p0、不升级本机。契约负责人 2026-10-20 通知 session-protocol v2.4（495b475，SP-3）已定稿：【等待用户】选填「模块：<id>」或「模块：无」，DI-10 以它为准。

## 目标

1. **DI-10**：模块协调发来的事项，只要内容里能看出是哪个模块，就归到那个模块；打转计数、历史折叠、三个选项、「继续等」都按归到的模块算。
2. **DI-11**：巡视停了，不用打开主视图你也会被提醒：一个不依赖收件箱、也不依赖巡视会话的本机定时检查，发现巡视超时就弹 macOS 系统通知，写明去哪个会话、做什么。
3. **DI-12**：模块不在「出手」时不算停滞：停滞计时不早于最近一次答复送达，等你、等批准（含答复没发出去的那段）、等其他线的时间都扣掉。

## 现状（已核对 main 1c2d3c9 与 di-p0 阶段丙真实数据，只读）

- **模块归属只判一次**：`loops.tag` 在事项第一次被看到时写 `module`，写了 `null` 就再也不重判。模块协调的事项只拿「要你决定」第一行和 module-crew `waitUser.decide` 逐字比；阶段丙模块会话写「是否允许**我**对…」，模块协调转成「是否允许**它**对…」，所以比不上。
- **阶段丙的三项**：#61「zeta 到 G1，是否允许它再跑一次 zeta 的单测（C184）」带交审编号；#62、#63 不带编号，但「要你决定」里写了「zeta」。三项 `module` 都是 `null`，主视图标「模块未知」。
- **连带失效**：`view._loop_of` 按 `module` 找打转事实，找不到就没有抬头字段、历史折叠和三个选项；`hub` 只在事项属于打转模块时才认「N 继续等」，所以「63 继续等」记成 `loopOption: None`，没静音；打转提示一直挂着，`stall._hushed` 又把停滞信号②压住。
- **巡视提醒只在主视图**：`hub.patrol_alarm` 在巡视 15 分钟没跑时出「⚠ 巡视 N 分钟没跑」，只有你打开主视图才看得到；收件箱在巡视 10 分钟没跑时自己代跑一轮（hub-patrol），所以收件箱不被叫醒时就没人跑、也没人提醒。
- **停滞起点**：`stall._module_findings` 从「最后一次提交，没有就 startedAt（会话登记时间）」算起；扣掉的等待只有「认得出模块的事项，从收到到收件箱记下你的答复」加上 module-crew 自己记的等待。答复没发出去的那段、合问（#44 是 delta、epsilon 合问，`multi`）、模块协调开的等待记录都没扣。

## 要你确认的假设

1. **反查顺序**（DI-10），前一条认出来就停：
   1. 事项自带模块：审批类的 `approvalModule`，或 v2.4 的「模块」字段（见假设 2）；
   2. 「要你决定」或「要点」里的交审编号（`C\d+`）在这个模块协调的 module-crew 事实里属于某个模块（`asks.refs`、`waitUser.ref`、`answers.ref` 任一处）；
   3. 内容里出现某个模块会话的邮箱名（如 rh2-zeta）；
   4. 「要你决定」里作为独立词出现、且只出现一个这个模块协调手上的模块 id（如「zeta」；前后不是字母、数字、`-`、`_`）；出现两个以上不猜；
   5. 都没有才记「模块未知」。
   普通开发线（不是模块协调）照旧取能力图当前模块。
2. **v2.4「模块」字段**：协议升到 v2.4（钉 495b475，样例按契约 `git archive` 覆盖，新增 wait-user/module-id、module-none、module-with-kind）。写了模块 id 就用它，不校验能力图里有没有；写「模块：无」表示跨模块或线级事项，不反查、不显示「模块未知」，抬头写「线级」，不参与任何模块的打转计数和停滞扣除；没写才按 2～4 步反查。
3. **重判**：记成「模块未知」的事项，之后每次重算都按假设 1 的第 2～4 步再判（只看内容，不看当前模块，免得旧事项被归到后来开的模块）；已经认出模块的不再改。
4. **DI-11 的定时检查**：
   - 是一个 launchd 任务（`~/Library/LaunchAgents/` 下一个 plist，每 5 分钟运行一次），运行固定路径的转发脚本 `~/.decision-inbox/bin/decision-inbox patrol-watch <组>`，不用模型、不开会话；
   - 判据和主视图同一个（`patrol_alarm`：巡视超过 15 分钟没跑完一轮，或登记后 15 分钟还没跑完过）；
   - 超时就发一条 macOS 系统通知，标题「决策收件箱：巡视停了」，正文写明巡视停了多久、去哪个会话（巡视会话名和链接）、做什么（同主视图的修法）；同一次停摆 30 分钟内不重复通知，之后每 30 分钟提醒一次；
   - 巡视恢复后不再通知，主视图那行也消失（macOS 已弹出的通知收不回来，这里的「提醒消失」指不再弹、主视图不再挂）；
   - 它只提醒，不代替巡视去跑，也不叫醒巡视会话（脚本没法给桌面版会话发消息）。
5. **装与卸**：`hub-setup` 的预览里写明要装这个 launchd 任务，你确认后才装；`teardown` 卸掉（`launchctl bootout` 后删 plist）；`doctor` 加一项「巡视提醒」：装了且已加载 ok，没装 bad 并给出装的命令。冻结期间不在本机装，只在测试里用假的 `launchctl`、`osascript` 验证，实机只在 scratchpad 的临时组上手动跑一次 `patrol-watch` 弹一条通知给你看（不装 launchd）。
6. **DI-12 的出手起点** = 下面几个时间里最晚的：模块最后一次提交、module-crew 的 `startedAt`、这个模块最近一次答复送达（module-crew `answers.at`，以及收件箱这一侧这个模块事项的答复**发送成功**时间）。
7. **DI-12 扣掉的等待**：
   - 这个模块的事项：从收到到答复**发送成功**（不再是到收件箱记下答复）；答复一直没发出去就一直算等；
   - 合问事项（一项问了几个模块）：对它涉及的每个模块都算等；
   - module-crew 自己记的等待照旧；
   - 模块协调开的等待记录（等其他线）：等待内容里点名了模块 id 的只扣那个模块，没点名的扣这个模块协调手上所有在做的模块。
8. 「模块未知」的事项不参与 DI-12 的扣除（它属于谁不知道）；按假设 3 后来认出来了就参与。

## 风险

- 第 4 步按模块 id 认词可能误认（例如模块叫 `api`，文字里提到别的 api）。缓解：只认「要你决定」这一行、只在恰好一个时认、只认这个模块协调手上的模块 id。
- launchd 跑的是转发脚本，插件升级后由插件改写转发脚本，plist 不用重装；转发脚本指向的插件目录不在时，`patrol-watch` 无法运行，`doctor` 会报出来。
- macOS 通知需要「脚本编辑器」的通知权限，第一次可能不弹；`doctor` 无法检测这一点，README 写明怎么开。
