# Spec: decision-queue

> 能力图模块 `decision-queue`。需求来源：`docs/requirements-record.md` 第 3.3.1～3.3.2 节、第 4.1～4.4 节、第 6.1 节第 4 条、第 6.4 节，第 12 节第 7、12 项。

## 目标

管理待答表，也就是「等你决定」的事项，从收到到结束的全过程：
- **收单**：校验【等待用户】，不合格就生成退回说明；合格就编号入表。
- **有效性标记**：取代、撤回、并行。
- **排序**：挡住的线越多、等得越久，排得越前。
- **解析你的回复**：字母答复、复制块、自己写的一句话、一次答多项。对不上或含糊时先问，不转发。
- **生成要转达的答复**：多线事项给每个适用会话各发一份。
- **跟踪事项状态**：答复转达之后，跟踪到对方恢复干活为止。

本模块只产出要发的文本和收件人。实际发送由收件枢纽会话调用 agent-relay 的 `bridge_send` 完成，发完把消息编号交回本模块记录。

## 已定事项（用户 2026-10-16 确认）

1. **第 12 节第 7 项：按状态跟踪，卡住就报异常。** 状态依次是：待答 → 已转达 → 已取走 → 已确认 → 已结束。
   - 「已取走」和「已确认」取自 agent-relay 的投递事实：`deliveryState` 为 `accepted`，以及 `acknowledgedAt`。
   - 「已结束」看提出方发来的【已恢复】：结束行写了这个事项编号就算结束。
   - 卡住的事项由 line-health 和 patrol 判断、去叫醒对方；本模块只提供状态和时间。**不重发答复，也不替对方关单。**
2. **第 12 节第 12 项：防伪造靠发件人校验，再加记编号。**
   - 依靠 agent-relay 的发件人校验，加上约定规则「开发线只认收件枢纽发来的答复」（需求第 4.2 节），不做签名或令牌。
   - 本模块在事件日志里记下每条答复发出时的 agent-relay 消息编号，供 `/item` 核对「这条答复确实是枢纽发的」。

## 范围

**范围内**

- 收单：【等待用户】和【撤回】，以及【等待用户】开头的【取代 #N】【与 #N 并行】。
- 生成退回说明的文本。
- 编号：用 group-store 的共用编号序列。
- 收单时按当时的登记算出审查标签，存进事项。之后登记变了也不改，对应需求第 4.3 节「新事项适用」。
- 排序。
- 解析你的回复并生成答复；多线事项分发给各适用会话。
- 记录已发答复的消息编号；按 agent-relay 的投递事实和【已恢复】更新状态。

**范围外**

- 发消息、读邮箱：由收件枢纽会话调用 agent-relay。
- 【等待其他会话】和等待单：归 wait-tickets。【等待用户】开头的「结束：#旧编号」原样存进事项，由 wait-tickets 读取。
- 判断事项卡没卡住、叫醒：归 line-health 和 patrol。
- 显示格式：归 hub-view。
- 「要你去原会话亲自确认」（宿主权限）：它来自会话的在线状态，不是收件箱里的事项，归 hub-view 算进「等你决定」。

## 关键决策与取舍（请重点审）

1. **收件人以 agent-relay 的发件人为准，不看正文里的「来自」。** 「来自」只用于显示。这样即使有人把「来自」写错，答复也只会回到真正的发件人那里。
2. **只有总协调和负责人可以抛多线事项**（需求第 4.4 节第 1 条）。开发线发来的事项即使写了「适用会话」，也按普通事项处理，只转给发件人，并带提示 `multiline-not-allowed`。适用会话里的名字必须是名册里的短名，否则退回，问题代码 `scope-session-unknown:<名>`。
3. **「挡住几条线」怎么算**：
   - 多线事项：等于「适用会话」的条数；
   - 普通事项：「是否完全停住」为「是」时记 1，为「否」时记 0。

   排序先按「挡住几条线」从多到少，再按收到时间从早到晚。这里不看等待单，因为等待单的关单要用到本模块，反过来依赖会形成环；这一点能力图评审时已经定过。
4. **回复解析从严**（需求第 6.4 节、第 4.2 节）。下面这些情况一律不转发，而是生成一句要问你的话：
   - 编号不存在，或者事项已经不在待答状态；
   - 字母不在原选项里；
   - 一条回复里同一项出现两个不同的选项；
   - 这一项已经转达过，又回了不同的选项；
   - 没写编号，又不止一项在等你。

   能解析的三种写法：
   - 「12 B」：转发时附上「选项 B 原文」；
   - 复制推荐块「12 A 〈原文〉」：原样转发；
   - 「12 自己写的一句话」：原样转发，不对应字母。

   一次答多项时按行切分，或者按「，」「；」切分，每段以编号开头。
5. **「审查中，请勿先批」不扣住答复**（需求第 4.3 节第 5 条）：你仍然回了的，照原话转发，不改写。
6. **取代和撤回只能作用于同一发件人自己的事项。** 作用于别人的事项时退回，问题代码 `not-owner`。被取代、被撤回的事项状态记为「已失效」，不删除。

## 状态与数据

事项状态：`pending` 待答、`forwarded` 已转达、`picked` 已取走、`acknowledged` 已确认、`closed` 已结束、`superseded` 已取代、`withdrawn` 已撤回。后两种在主视图里合称「已失效」。

快照放在 group-store 的领域 `items`。每个事项记这些内容：编号、发件人身份名、收到时间、原文全文、解析出的要点（来自、要你决定、选项、推荐、是否完全停住、适用会话与各线范围、结束行）、收单时的审查标签（含「⚠ 未标审查」时正文里提到审查的原句）、状态与各状态的时间、已发答复的消息编号和收件人。事件类型：`items.received`、`items.returned`、`items.superseded`、`items.withdrawn`、`items.answered`、`items.sent`、`items.delivery`、`items.closed`。

## 接口约定

```python
from decision_inbox import items

r = items.receive(g, text, sender="fe-codex", relay_id=2927, received_at="...")
r.handled         # 这条消息归不归本模块（【等待用户】【撤回】为 True，其他为 False）
r.accepted        # 是否入表或生效
r.item            # 新事项编号，或被撤回的编号
r.problems        # 退回原因（message-protocol 的问题，加上本模块的 scope-session-unknown、not-owner）
r.hints           # 例如 multiline-not-allowed、message-protocol 的 no-recommendation
r.return_text     # 不合格时要发回给发件人的退回说明，合格时为 None

items.pending(g)                  # 待答事项，已按决策 3 排好序；每项带 blocks（挡住几条线）
p = items.interpret_reply(g, "12 B\n13 A")
p.answers         # (Answer(item=12, letter="B", original="12 B"), ...)
p.question        # 对不上或含糊时要问用户的话；有它时 answers 为空
out = items.answer(g, p.answers, answered_at="...")   # 记为已答，返回 (Outgoing(to="fe-codex", text="【用户答复】…", item=12), ...)
                                  # 有事项已不在待答状态时抛 ValueError，什么都不写（防止重复转达）
items.record_sent(g, item=12, to="fe-codex", relay_id=2950, at="...")
items.update_delivery(g, {2950: ("accepted", None)}, at="...")   # 消息编号 → (deliveryState, acknowledgedAt)
items.on_resumed(g, message, sender="fe-codex", at="...")        # 【已恢复】结束行里提出方自己的、已转达之后的事项记为已结束；
                                  # 返回这次结束的事项编号；还在待答的事项不受影响（要放弃请用【撤回】）
items.history(g, item=12)         # 该事项的事件，按先后排序，供 /item
items.get(g, item=12)             # 按编号取一个事项（带 no），没有返回 None，供 hub-view 的详情
items.by_status(g, "superseded", "withdrawn")   # 按状态列出事项（带 no），按编号排序，供 hub-view 的刚转达与失效
```

- 【用户答复】的文本一律由 message-protocol 的 `format_user_reply`、`format_multiline_replies` 生成，本模块不拼字符串。
- `update_delivery` 只接收「消息编号 → 投递事实」的对应关系，由调用方用 relay-reader 解析 `bridge_outbox` 后传入。本模块不依赖 relay-reader。
- 退回说明是给发件人看的普通文本：列出每条问题的中文说明，请对方补全后重新抛出。它不是需要再被解析的消息类型。

## 依赖

- 本插件模块：group-store（编号、状态、事件、名册）、message-protocol（解析与生成答复）、review-registry（收单时的审查标签）。
- 外部组件：agent-relay。本模块不调用它；调用方用 `bridge_send` 发出答复和退回说明，并把 `bridge_outbox` 的投递事实交回本模块。用到的都是现有接口，不缺。

- 收单、退回、取代、撤回、排序、各种回复写法、多线分发、状态推进逐项断言；状态变化同时核对事件日志。

## 边界

- **始终**：用户原话一字不改；对不上或含糊先问；收件人以 agent-relay 发件人为准；保留全部事项和事件。
- **先问**：改变排序规则；放宽回复解析；让本模块自己发消息。
- **绝不**：替用户选选项、补全或合并选项；重发答复；替提出方关单或结束事项；扣住「审查中」事项的答复。

## 验收标准

1. 合格的【等待用户】：入表，编号来自共用序列；事项里存了原文、要点、收单时的审查标签；事件 `items.received`。
2. 不合格的【等待用户】，例如缺「要你决定」或多线缺一条范围：不入表、不占编号；`return_text` 逐条列出问题的中文说明；事件 `items.returned`。
3. 适用会话里有名册中不存在的短名：退回，代码为 `scope-session-unknown:<名>`。开发线写了「适用会话」：按普通事项入表，带提示 `multiline-not-allowed`，答复只转给发件人。
4. 【取代 #N】：同一发件人的 N 变为 `superseded`，新事项入表；作用于别人的事项时退回，代码为 `not-owner`。【撤回】：同一发件人的事项变为 `withdrawn`。
5. `pending` 的排序：多线 3 条线的排在普通「完全停住」事项前面，后者又排在「否」的前面；挡住数相同时，先收到的在前。
6. 「12 B」：解析为第 12 项选 B；生成的答复里用户原话是「12 B」，并附「选项 B 原文」。复制块「12 A 〈原文〉」原样转发。「12 自己写的一句话」原样转发，不对应字母。
7. 「12 B\n13 A」和「12 B，13 A」都解析为两个答复。
8. 下面这些情况都只返回 `question`，不产生答复：编号不存在、第 12 项已撤回、字母 D 不在选项里、「12 A，12 B」、已转达 A 后又回 B、没写编号却有两项在等。
9. 多线事项（适用会话：前端、API）答复后：产生三份外发，分别给发件人、前端、API。后两份的「适用于你的范围」等于原事项里写给它们的那一条。
10. 「审查中，请勿先批」的事项照样可以答复和转发，原话不变。
11. 状态推进：`answer` 后为 `forwarded`；`record_sent` 记下消息编号；`update_delivery` 收到 `accepted` 后为 `picked`，收到 `acknowledgedAt` 后为 `acknowledged`；提出方发来【已恢复】、结束行写了该编号后为 `closed`。别人的【已恢复】不改变这个事项的状态；还在 `pending` 的事项也不因【已恢复】改变（2026-10-16 用户确认：放弃未答事项要用【撤回】，免得事项从待答表里悄悄消失）。
12. `history(g, item=12)` 按先后列出收单、答复、发送（含消息编号）、投递、结束各条事件。
13. 所有状态变化都写入 `items` 快照和事件日志，`store show` 的一致性检查为正常。

## 假设

1. 收件枢纽会话按约定把收到的每条【等待用户】【撤回】原文和 agent-relay 的发件人、消息编号交给本模块，答复发出后再调用 `record_sent`。约定块的具体写法在 onboarding 定。
2. 一个事项的答复可能发给多个收件人，以多线事项为例；只有所有收件人都确认后，事项才进入 `acknowledged`。只要有一个还没取走，就停在前一个状态。
