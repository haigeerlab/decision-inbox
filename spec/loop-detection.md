# Spec: loop-detection

> 能力图模块 `loop-detection`（2026-10-19 用户确认插入，排在最后，不插队）。来源：R21「模块打转」分派给本插件的 DI-5、DI-6（`livesaas-integration/REQ-R21-STUCK-MODULE.md`，依据用户决定 58–61）；R21 拆成 4 个模块，这是第 2 个。插入时的假设 1–11 用户 2026-10-19 确认。Spec 2026-10-19 批准后修订一次：选项「换做法」改为「换方案」并同步已有 R14 文字（第 9 节），用户定，待复审。判法与 module-crew 下一版已对齐（共享笔记 `di-6-answers-field.md`）。

## 目标

用户每次被问，一眼看出是哪个项目、哪个模块、第几次（超没超基准）、答了几次进度没动、真正干活多久、进度多少；模块打转时系统自己发现，在该模块来问的那一项顶上给出挂起、换方案、继续等三个现成选项。只提示，不硬拦。

## 现状（已核对代码）

- **事项**（`items._record`）：交审事项有 `approvalModule`、`approvalNode`、`project`；普通【等待用户】没有模块。module-crew 协调线上，模块会话只和协调会话说话，事项的发起方是协调线（`crew-coordinator-seam`）。
- **卡片抬头**：普通卡片 `━━ N · <线> · <要你决定首行> · <多久前>`（`view._item_card`）；交审全文 `━━ #N · 项目 · 模块 · 审 节点 · 多久前`（`view.render_approval`）。没有次数、基准、时长、进度。
- **数据来源**：
  - spec-guard `/map --json`：`activeModule`、每个模块 `progress`、`lastTickAt` 等（`specguard.ModuleFact`）；0.77.0 起每个模块有 `gates: {"total","done"}`，本插件还没读。
  - module-crew `sessions --json`：本插件读了 `startedAt`、`commits`、`asks`、`waitUser`（只取「有没有开着的」）；0.5.0 起有 `answers: [{ref, at, commitsAfter, ticksAfter}]`，还没读。
  - 等待记录（`tickets`）：`sentAt`、`close.at`，是「等别的线」的时段。
- **停滞判断**（`stall.py`）：按模块的判断跳过有开着的【等待用户】或正在审查的模块（第 73 行）；停滞时长按墙钟算（`now − 最后提交或开工`）。
- **线状态**（`health.py` 第 220–222 行）：这条线有完全停下的待决事项时写「阻塞：等你决定 #N」，去会话操作事项也这样写。
- 主视图读进度表、crew 事实的地方：`__main__` 的主视图、答复、巡视三处都已读好 `maps`、`crews` 传给 `hub.main_view`／`patrol.plan`。

## 要做的

### 1. 事项打标（假设 1）

- 新模块 `decision_inbox/loops.py`。每次出主视图或巡视前，给还没打标的事项打上 `module`（之后不改）：
  - 交审事项：`approvalModule`；
  - 单模块开发线：这条线进度表的 `activeModule`；
  - module-crew 协调线：「要你决定」第一行与某个模块 `waitUser` 的 `decide` 相同，就是那个模块；对不上记 `null`；
  - 多线事项、读不到进度表：`null`（显示「模块未知」，不参与下面所有计数）。
- 打标写进事项记录（`module` 字段），记一条事件 `items.module-tagged`。

### 2. 每个模块的事实（`loops.facts`）

对每个「在做的模块」（单模块开发线的 `activeModule` 且阶段不是 DONE；module-crew 未合入、未挂起的模块）算：

| 事实 | 算法 |
|---|---|
| 问了 n 次（假设 2） | 打标为这个模块的事项数，已关的也算；不算去会话操作，不算被取代的 |
| 基准 M（假设 3） | 2 + `gates.total`（这条线进度表里这个模块的；module-crew 模块读协调线仓库的进度表）；读不到写「基准未知」 |
| 超出第 k 次 | n > M 时 k = n − M |
| 答复与段（假设 4） | 段 i 从第 i 次答复起到下一次答复（最后一段到现在）。module-crew：直接用 `answers` 的 `commitsAfter`、`ticksAfter`，都是 0 算「没动」，有 null 算「读不到」。单模块线：答复时间取这个模块事项的答复时间；只读这条线仓库 `git log --first-parent HEAD` 的提交时间，段内没有提交算「没动」；git 读不到算「读不到」 |
| 你答了 j 次进度没动 | 「没动」的段数 |
| 开工时长（假设 5） | 起点：module-crew 用 `startedAt`；单模块线用这个模块第一个事项的收到时间。扣掉：这个模块有事项在等用户的时段（收到 → 第一次答复，没答的到关闭或现在；去会话操作也算）；单模块线另扣这条线有开着的等待记录的时段（module-crew 的等待记录分不出模块，不扣）。重叠时段只扣一次 |
| 进度 a/b | 进度表里这个模块的 `progress` |
| 最后一次进展 | module-crew：`commits.last.at`；单模块线：git 最新提交时间与 `lastTickAt` 取晚的 |

### 3. 打转判断（假设 6，阈值可配）

满足任一条就算打转：

- **①答了 2 次进度没动**：取「后面又来问过」的段（段起点之后这个模块又收到过事项）里最后 2 段，都「没动」。还在进行中的最后一段不算，免得刚答完就误判。
- **②没进展的出手时间满 12 小时**：每个「没动」的段，取段起点到这段里下一次来问（没有就到现在）的时长，加起来满 12 小时。
- 有「读不到」的段：不判，模块行写「进度读不到」。
- 阈值放在 group.json 的 `stall` 下：`loopAnswers`（2）、`loopHours`（12）、`loopQuietHours`（12）。

### 4. 命中以后（假设 7）

- **事项顶上的提示**：这个模块每个开着的事项（普通卡片和交审全文都算），在抬头上面加：
  ```
  ⚠ 模块 <id> 可能在打转：<命中原因，例如「你答了 2 次进度没动」或「没进展的出手时间累计 13 小时」>
    A 挂起它，先开可开工的模块（<列出来>）：回「N 挂起」
    B 换方案：回「N 换方案：<怎么换>」
    C 继续等，12 小时内不再提示：回「N 继续等」
  ```
  可开工的模块沿用 R14 的写法（进度表里 status 为 ready 的模块）。
- **答复**：「N 挂起」「N 换方案：…」「N 继续等」算对事项 N 的答复，照常转【用户答复】给发起方，选项原文带上（挂起由那条线自己用 spec-guard 的 module-suspend 或 module-crew 的做法做，决策收件箱不代做）。选 C 时记下这个模块 12 小时内不提示（状态 `loops.quiet`）。原来的字母答复照旧可用，两种不能写在同一段里。
- **主视图停滞提醒**：命中期间，主视图顶部（去会话操作一栏之后）挂一行「⚠ 模块 <id>（<线>）可能在打转：<原因>；等它下次来问时在那一项上选，或去会话里说」。
- **巡视不再叫线抛一项**：命中且不在安静期的模块，R14 对这个模块（单模块线是这条线）的停滞、报批多次叫醒都跳过。
- 去会话操作事项上不加提示。

### 5. 抬头与折叠（DI-5）

- **抬头**：普通卡片与交审全文的第一行都改为
  `━━ #N · <项目> · 模块 <id> · <节点或类型> · 第 n 次问你（基准 M[，超出第 k 次]）· 你答了 j 次进度没动 · 开工 X 小时 · 进度 a/b · <多久前>`
  - 项目：事项的「项目」字段，没有就用这条线进度表的标题，再没有用线名；
  - 节点或类型：交审写「审 <节点>」，普通事项写「等待用户」；
  - 模块未知时只写到「模块未知」，后面的计数都不写；某项读不到写「…读不到」。
  - 交审卡片原来的「项目／线」第二行、本项第几次交审等内容照旧（R12 原样展示）。
- **折叠历史**：每张卡片下面加「同模块之前问过：」，每个之前的事项一行 `第 i 次 · <要你决定首行，截短> · <结果>`（结果：答了 X／已关／已失效／去会话操作已结项）；最多显示最近 5 行，更早的写「还有 m 次，回『看模块 <id>』看全部」。
- **看模块**：新回复「看模块 <id>」列出这个模块的全部事项（每项一行，同上）和第 2 节的事实。

### 6. 主视图「在做的模块」

线状态行之后加一段，每个在做的模块一行：
`<线> · 模块 <id> · 问了 n 次（基准 M）· 开工 X 小时 · 最后一次进展 Y 前[ · ⚠ 可能在打转]`。没有在做的模块时不显示这一段。

### 7. 停滞判断改用出手时长（假设 8）

- `stall._module_findings`：去掉「有开着的【等待用户】或正在审查就跳过」；停滞时长改为「从最后一次提交（没有就开工）到现在」的出手时长，扣掉第 2 节说的等用户时段。
- 安静停住（线级「停住」）照旧按 R14。

### 8. 线状态措辞（假设 10）

`health.py`：去会话操作事项让线阻塞时写「阻塞：等你去会话操作 #N」；普通事项照旧「阻塞：等你决定 #N」。

## 关键决策与取舍

1. **打标在出主视图或巡视前做，不在收件时做**：收件路径没有进度表，读一次要起子进程；hub-loop 收件后马上出主视图，时间差可以忽略。打完就固定，模块切换后旧事项不跟着变。
2. **单模块线只看提交**：spec-guard 只给最近一次勾选时间，分不出每段勾了几项；todo 勾选通常随提交进库。
3. **①只看「后面又来问过」的段**：module-crew 的最后一段算到现在，刚答完时为 0；不排除会在用户刚答完时误报。
4. **选项用词，不用字母**：事项自己的选项已经占了 A、B、C，打转选项用「挂起／换方案／继续等」回复，避免冲突。不改契约：选项原文写进【用户答复】正文。
5. **只提示不硬拦**（R21「不做的」）：不拦线抛事项、不替线挂起。

## 验收标准

1. 单模块开发线：两次答复后都没有提交，第 3 个事项来问时，卡片顶上出现打转提示（原因「你答了 2 次进度没动」）和三个选项；中间有一次提交就不出现。
2. module-crew 线：`answers` 最后两段 `commitsAfter`、`ticksAfter` 都是 0 时同上；有 null 时不判，模块行写「进度读不到」。
3. 没动的段出手时间累计满 12 小时：提示原因为②；等用户的时间不算进去。
4. 抬头字段齐全：项目、模块、节点或类型、第 n 次（基准 M、超出第 k 次）、j、开工时长、进度；去会话操作和被取代的不计入 n；开工时长扣掉了等用户（含去会话操作）和等别的线的时间。
5. 读不到 gates（旧 spec-guard）：写「基准未知」，不算超出；模块未知时抬头只写到「模块未知」。
6. 同模块之前的事项折叠成一行一项，超过 5 项时有「看模块」提示；「看模块 <id>」列出全部。
7. 回「N 继续等」：照常转【用户答复】，12 小时内这个模块不再出提示；回「N 挂起」「N 换方案：…」照常转发并带选项原文。
8. 命中期间巡视不对这个模块发 R14 叫醒；主视图顶部有停滞提醒一行。
9. 有开着的【等待用户】或正在审查的 module-crew 模块也会被停滞判断看到；正在等用户的时段不算停滞时长。
10. 去会话操作让线阻塞时，线状态写「阻塞：等你去会话操作 #N」。
11. R14 叫醒文字、主视图逾期行和规则段里不再出现「换做法」，改为「换方案」。
12. 全量测试通过，旧称扫描通过。
