# Spec: approval-display

> 能力图模块 `approval-display`（2026-10-19 用户确认插入，排在 review-nearby 之后）。来源：`livesaas-integration/REQ-REVIEW-NEARBY.md` 的 R12（取代 R8）、R15、R17，以及用户决定 46、47（协调人转述，用户 2026-10-19 在本会话确认采纳）。做法假设 1–9 用户 2026-10-19 在本会话确认。

## 目标

1. 你在决策收件箱就能读到要审的东西的原文：产物全文、开发会话的交审原文、审查结论原文，不摘要、不截断、不改写。读不到时写明是哪一条读不到、为什么。
2. 原文前面补上你切过来需要的背景（项目、能力图位置、模块、节点、第几次交审、相关决定），后面补上「批准会发生什么」和待你决定的问题，推荐放在最后，只作参考。补充的内容和原文分开标出。
3. 最终验收项把「验收标准 ↔ 证据」对照表放在最前面，标出缺证据的条目。
4. 协作规则段写明：要你决定的事只在决策收件箱问，其他会话不留可以点的决定按钮；某项已经在别处定了，就收回旧提问。
5. 没有新字段的事项（普通开发线）显示和现在一样。

## 现状（已核对代码与需求）

1. 事项卡片只显示「要你决定」、选项、推荐答复（可复制代码块）、审查标签。要点、交审原文、产物都不显示，你只能照着推荐抄（批 2 #20、#21、#23）。
2. 「N 详情」能显示那条【等待用户】的原文，但看不到它引用的文件和交审原文。
3. 能力图位置：spec-guard 的 /map 出口（`specguard.read_line`）已经接好，主视图和 `/map` 在用，事项卡片没用到。
4. review-nearby 已经在事项里存了「要点」原文（`brief`）和待用户决定（`decisions`）。
5. 契约 v2.0.1 的【等待用户】没有取原文的字段。

## 要做的

2. **取原文**（新模块 `sources.py`，只读）：

   - 读不到时记下原因：文件不在、不在 git 仓库里、提交不存在、指纹对不上、读取超时。不拿别的内容顶替。

   ━━ #24 · <项目> · 模块 <id> · 审 <节点>                      【决策收件箱补充】
   项目：<项目名>（<仓库路径>，<分支>）· 线：<线名>

   相关决定：<同一发件会话、同一模块过去的答复：编号、日期、你原话的第一行>
   ━━ 验收标准与证据（只在最终验收）                           【对照】
   ━━ 开发会话的交审原文                                       【原文】

   ━━ 批准会发生什么                                           【决策收件箱补充】

## 关键决策与取舍（请重点审）

1. **主视图只完整展开一项**：几项全文同时放进主视图会很长，没法读。只展开排第一的一项，其余各一行、回「看 N」展开。这样做不会截断任何一项的原文。
2. **每次现读原文，不存副本**：保证你看到的就是提交上的内容。代价是每次展示都要跑 git，原文文件被删了也就读不到了，所以在契约里约定原文文件在结项前不得删改。
3. **读不到就明说，不降级成摘要**：这是 R12 的硬要求。宁可显示「原文取不到：提交 4c5d6e7 不存在」，也不拿要点顶替。
4. **决策收件箱不判断证据是否充分**：它只做对照、标出缺的，判断留给你。
5. **推荐不再放可复制的代码块**：这是 R12「不在显眼处给可复制的答案」的要求。普通事项（不是审批项）的复制块保留，免得改动面太大。
