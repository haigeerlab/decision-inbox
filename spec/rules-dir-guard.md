# Spec: rules-dir-guard

> 能力图模块 `rules-dir-guard`（2026-10-20 用户确认插入，排在 my-waits 之后）。来源：2026-10-20 实测，在协作组目录（各成员目录的上级）开新收件箱会话跑 `/decision-inbox:hub-setup`，收件箱规则段写进了组目录的 CLAUDE.md，被下面的审查者会话一起加载；原来收件箱目录的 CLAUDE.md 还留着旧规则段；doctor 仍报通过。下面的假设用户 2026-10-20 已确认。

## 目标

协作规则段只会写到它的主人的目录里，不会写到别的成员沿父目录加载得到的地方；换目录重跑接入时不留下没人管的旧规则段；万一出现了，doctor 报出来。

## 现状

- `onboard.hub()` 把规则段写进 `--project` 下的 CLAUDE.md，`hub-setup` 传 `--project "$PWD"`；写之前不核对这个目录和其他成员目录的关系。`onboard.join()` 一样。
- `_commit` 把 onboarding.json 的 `files[<邮箱名>]` 直接改成新路径；旧路径的文件里的规则段没提示、没删。
- doctor 的 `_conventions` 只读 `files` 里记下的那个文件，有没有当前版本规则段；不看其他位置。
- Claude 会沿父目录一路加载 CLAUDE.md（还有同目录的 CLAUDE.local.md）；Codex 从项目根到当前目录加载 AGENTS.md。

## 假设（用户 2026-10-20 已确认）

1. **成员目录**：每个没有离开（不在 `left` 里）、不是只登记的旧格式（`legacyFormat`）的成员，它的成员目录是名册里的 `repo`（开发线才有）和 `files[<邮箱名>]` 所在的目录，两者都算。
2. **只看目录关系，不区分文件名和宿主**：上级目录里有规则段就算问题，不管它是 CLAUDE.md、CLAUDE.local.md 还是 AGENTS.md，也不管成员在 Claude 还是 Codex。偏保守，换规则简单。
3. **直接拦下**：不加「强行写入」开关；报错退出，什么都不写，报错里写明原因、涉及哪个成员的哪个目录、建议去哪个目录跑。
4. **旧规则段**：加 `--drop-old`，只删旧文件里本插件、同一角色的规则段；那个文件是接入时新建的、删完为空时删掉整个文件（同 leave）。hub 和 join 都加。
5. **doctor**：从每个成员目录往上到根目录，逐级看 CLAUDE.md、CLAUDE.local.md、AGENTS.md 里有没有 decision-inbox 标记，有就报 bad；查不到兄弟目录里的旧规则段（那个靠第 4 条在重跑时提示）。

## 要做的

### 1. 写入前核对目录（hub 和 join 共用）

设这次要写的规则文件所在目录为 T，其他成员（不含自己）的成员目录集合为 D：

- **拦下**：T 是 D 里某个目录本身或它的上级时，抛 `JoinError`，预览和确认都不写任何东西。「本身」也算，是因为同目录的 CLAUDE.md 和 CLAUDE.local.md 会被同一个 Claude 会话一起加载。和别的成员是同一个规则文件时，照旧由 `place` 报「已有别的角色的规则段」，不归这一条。
  报错写成：`不能把协作规则段写进 <规则文件>：<目录 T> 是 <成员短名>（<角色>）的目录 <成员目录> 的上级（或同一目录），在那里开的会话会一起加载这个规则段。请到 <建议目录> 重跑。`有几个成员就列几个。
  建议目录：本会话以前记下过规则文件（`files[<邮箱名>]`），而且那个目录本身不会被拦，就建议那个目录；否则 hub 建议 `<T>/hub`，join 建议「本会话自己的项目目录（不包含其他成员目录的那一层）」。
- **提示，不拦**：T 是 D 里某个成员**规则文件所在目录**的下级时（反过来：别人的规则段在我上面），在预览开头加 `⚠`：`<那个规则文件> 在本目录的上级，里面是 <成员短名> 的协作规则段，本会话会一起加载它；请让那个成员换到它自己的目录重跑接入（加 --drop-old 删掉这里的旧段）`。不拦，是因为要改的是别人的文件，本会话换目录也解决不了。

### 2. 换目录重跑时的旧规则段

`files[<邮箱名>]` 记下的旧文件 R 和这次的规则文件不是同一个文件、R 还在、里面有本角色的规则段时：

- 不带 `--drop-old`：预览开头加 `⚠ 旧规则文件 <R> 里还留着本会话的协作规则段：在那个目录开的会话还会按它工作。要一并删掉，加 --drop-old 重跑（只删这一段，文件里别的内容不动）`。
- 带 `--drop-old`：预览写明「确认后从 <R> 删掉旧协作规则段」（是接入时新建、删完为空的，写「确认后删掉这个文件」）；`--confirm` 时照做，并在 onboarding.json 的 `created` 里去掉 R，事件 `onboarding.joined` 的 data 里加 `droppedOld: <R>`。
- R 里的规则段是别的角色、或标记坏了：不删，提示「<R> 里的 decision-inbox 标记不是本会话的，没动它」。
- 带了 `--drop-old` 但没有旧段可删：预览写「没有旧规则段要删」，照常写入。

### 3. doctor 新检查「上级目录的协作规则段」

对每个成员目录 d（假设 1），看 d 本身和它所有的上级目录，每级的 CLAUDE.md、CLAUDE.local.md、AGENTS.md：文件里有任何一行 decision-inbox 的 BEGIN／END 标记，而且不是这个成员自己记下的规则文件，就报一项 bad：

- 名称：`上级目录的协作规则段：<文件>`；
- 证据：`<文件> 里有 decision-inbox <角色> 协作规则段，<成员短名…> 在它下面的目录里会一起加载`；
- 怎么做：这个文件是某个成员记下的规则文件时，写「让 <那个成员> 到不包含其他成员目录的目录重跑接入，加 --drop-old」；没人记下时，写「手动删掉 <文件> 里 BEGIN 到 END 这一段，或在那个目录运行 onboard leave」。

同一个文件只报一项，受影响的成员合在一起写。一个都没有时报一项 ok：`各成员目录及其上级目录里没有别的协作规则段`。只读文件，不写任何东西。

### 4. 命令行与文档

- `onboard hub`、`onboard join` 加 `--drop-old`。
- `commands/hub-setup.md` 第 2 步：要在决策收件箱自己的目录里跑（不是协作组的上级目录）；预览报「不能把协作规则段写进」就把原因和建议目录告诉用户，停下；预览里有旧规则文件提示就问用户要不要加 `--drop-old`。`commands/join.md`、`skills/decision-inbox-join/SKILL.md` 同样补一句。
- README 升级说明加 0.0.34 一条；版本号升到 0.0.34。

## 做 / 不做

- 做：上面 1～4。
- 不做：改规则段内容、按宿主区分文件名、改 leave／teardown、自动搬家（只拦下和提示，不替用户换目录）、升级本机、打标签。

## 验收标准

1. 组里已有审查者，目录是 `<组>/owner`；在 `<组>` 跑 `onboard hub`（预览和 `--confirm` 都试）：退出码非 0，报错里有原因、审查者的目录和建议目录 `<组>/hub`（以前记下过就是记下的那个目录），什么文件都没写。
2. 同上，审查者的目录就是 T 本身（例如开发线 repo 和收件箱同目录）：一样拦下。
3. `onboard join` 的目标目录是收件箱或其他成员目录的上级：一样拦下。目标目录在收件箱规则文件目录的下级：不拦，预览有 `⚠` 提示。
4. 收件箱以前记在 `<组>/hub/CLAUDE.md`，换到 `<组>/inbox` 重跑：不带 `--drop-old` 时预览有旧规则段提示，旧文件不动；带 `--drop-old --confirm` 后旧文件只少了规则段（文件里别的内容逐字不变），接入时新建、删完为空的旧文件被删掉，`created` 里没有它了。旧文件里是别的角色的段时不动它。join 一样。
5. doctor：`<组>/CLAUDE.md` 里有收件箱规则段、审查者在 `<组>/owner` 时报 bad，写明文件和受影响的成员；把那一段删掉后这一项报 ok；成员自己记下的规则文件不会被当成问题；离开的成员不算。
6. 每条修复先有一条失败的测试；全量 `PYTHONPATH=tests:. python3 -m unittest discover -s tests` 通过。

## 风险

- 成员目录在家目录下时，doctor 会一路查到根目录，多读几个文件；只读、只判断标记，代价很小。
- 以前就在上级目录建过收件箱的组，升级后重跑 hub 会被拦下：这正是要的，报错写明该去哪。
- 偏保守（假设 2）：Codex 成员的 AGENTS.md 在 Claude 成员的上级时也会被拦或报 bad，虽然 Claude 实际上不一定加载它；换来的是规则简单、不用猜宿主怎么加载。
