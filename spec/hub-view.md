# Spec: hub-view

> 能力图模块 `hub-view`。需求来源：`docs/requirements-record.md` 第 6 节（显示格式）、第 4.3 节（审查状态行的显示）、第 4.5 节（等待与关闭的展开）、第 7 节 `/flow` 的「全线停住」主动推送。

## 目标

生成收件枢纽的主视图，以及用户说「编号 详情」「看等待」「看已关闭」「看失效」时的展开视图。主视图按需求第 6.1 节的固定顺序排列：
1. 各线；
2. 总览；
3. 异常；
4. 等你决定的卡片；
5. 最后一行计数。

盯这个窗口的只有用户，所以按实验里用户的实际习惯来设计：大多直接采纳推荐、常看不懂选项区别、会把几个复制块都发出去、最常问「是不是又停了」。

本模块只把已有的数据排版成文字。不判断状态、不检测信号、不解析回复、不发消息。

## 已定事项（用户 2026-10-16 确认，12 条格式）

1. 输出 **Markdown**。每张卡片只有一个代码块作为复制块，只给推荐的那个选项；其余是普通文字，不用表格。
2. 什么事都没有时：只显示各线、总览「等你决定 0 项 · 异常 0」和最后一行计数。
3. 「各线」一行：`前端 干活中 · API 等你确认 · 后台 阻塞：等API · …`。状态文字取 line-health 给的，「阻塞：等 X」去掉中间的空格。
4. 「等你确认」（宿主权限）单独成一种卡片，排在所有卡片最前面：标题 `━━ 去原会话确认 · <短名> · N 分钟前`，下一行「要你做：打开「<短名>」会话，确认它弹出的请求（<agent-relay 给的 detail>）」。没有 detail 就不写括号。这种卡片没有选项，也没有复制块。它计入「等你决定 N 项」。
5. 有信号 1（全线互等）时，在「各线」之前加一行 `⚠ 全线停住 N 分钟：卡在 X`。X 是被等最多、而它自己没在等别人的会话；判断不出来时写「卡在哪见 /flow」。N 取这些等待单里最早一张已等的分钟数。
6. 异常行：每种信号配一句固定的建议（见「信号建议表」），写成「谁、卡在哪、建议你做什么」。
7. 时间：不到 1 小时写「N 分钟前」，不到 1 天写「N 小时前」，满 1 天写「N 天前」。
8. 复制块写 `<编号> <推荐字母> <你该回原文>`。「你该回」原文已经以推荐字母开头（字母后跟空格或冒号）时，不再重复字母。有推荐但没有「你该回」时，复制块只写 `<编号> <推荐字母>`。
   - 「你该回」原文以「数字＋空格」开头时（提出方猜的编号），先去掉这个数字再按上面处理，例如原文 `12 A 先接微信支付` 在事项 15 上写成 `15 A 先接微信支付`（用户 2026-10-16 验收时确认）。
9. 选项在卡片上只显示第一行，超过 30 个字截断并加「…」；「选了会怎样」照原文摘，不截断。
10. 「刚转达：编号 → 会话短名」只显示最近 10 分钟内转达的，按时间算。
11. 来源：普通事项写短名，多线事项写「多线：前端＋API」。
12. 展开视图：
    - 「编号 详情」：原文全文、各线范围、agent-relay 消息编号；
    - 「看等待」：开着的等待单，每张一行，带提醒标记；
    - 「看已关闭」：今天已关的单，带理由和依据；
    - 「看失效」：已取代和已撤回的事项，每条一行。

## 主视图样例

```text
⚠ 全线停住 14 分钟：卡在 前端
前端 等你确认 · API 阻塞：等前端 · 后台 已结项（空闲）
等你决定 2 项 · 异常 1 · 刚转达：9 → API

异常
- API：交付了没人接——前端 已发消息给 API，API 还没去取。建议：提醒 API 去取前端的交付

━━ 去原会话确认 · 前端 · 14 分钟前
要你做：打开「前端」会话，确认它弹出的请求（permission prompt）

━━ 12 · 前端 · 支付页先接哪种支付方式 · 5 分钟前 · 挡住 1 条线
要你决定：支付页先接哪种支付方式
推荐 A：先接微信支付
  选了会怎样：本周能上线支付页，支付宝下周补
（下面是代码块，代码块里只有一行：12 A 先接微信支付）
B：先接支付宝
  选了会怎样：要多等三天 API 补签名接口
  回 12 B
审查：不需审：本会话无审查者 · 详情：12 详情

等待中 1 单 · 已失效 0 项 · 今天已关 3 单
```

## 写法细则（来自需求第 6.2、6.3、4.3 节）

- 卡片标题：`━━ <编号> · <来源> · <主题> · <多久前> · 挡住 N 条线`。主题取「要你决定」的第一行，超过 20 个字截断。挡住 0 条线时这一段省略。
- 选项按原文顺序；推荐的那个移到第一个，写「推荐 A：」。原文没写推荐时，不标推荐、不给复制块。
- 原文没写「选了会怎样」时，写「选了会怎样：提出方未说明后果」，不自己推断。
- 非推荐选项写「回 <编号> <字母>」。
- 审查行写「审查：<review-registry 给的标签> · 详情：<编号> 详情」：
  - 「审查中，请勿先批」加粗；
  - 「⚠ 未标审查」时，下面逐行写「  正文提到：<原文>」，原样摘出（需求第 4.3 节第 2 条）。
- 主视图不出现 agent-relay 的消息编号、指纹、文件路径（需求第 6.3 节第 1 条）。
- 最后一行只给数字：`等待中 N 单 · 已失效 N 项 · 今天已关 N 单`。已失效只写数量，不列编号。

## 信号建议表（已定事项 6）

| 信号 | 异常行写法（谁 / 卡在哪 / 建议） |
|---|---|
| 1 全线互等 | 不单列，已在第一行推送 |
| 2 交付了没人接 | 等待方：交付了没人接——<说明>。建议：提醒 <等待方> 去取 <被等方> 的交付 |
| 3 悄悄停下 | 会话：<line-health 的说明>。建议：问 <会话> 是否卡住，或让它继续或上抛 |
| 4 离线有积压 | 会话：<说明>。建议：打开 <会话> 让它恢复 |
| 5 长时间忙碌又有积压 | 会话：<说明>。建议：先等它做完这一轮；要插队就去它的会话说明 |
| 6 挂起挡住后面 | 会话：<说明>。建议：看挂起原因是否已经解决 |
| 7 反复返工 | 送审方：<说明>。建议：看一下这次审查的分歧点 |
| 8 进度变慢 | 会话：<说明>。建议：问 <会话> 进展，或交负责人跟进 |
| 9 孤儿等待 | 等待方：<说明>。建议：确认旧等待是否还需要，不需要就说「关掉 #编号」 |
| 10 空闲的 Codex 会话有积压 | 会话：<说明>。建议：在 Codex 里点开 <会话> 让它加载 |

## 范围

**范围内**

- 主视图：第一行推送、各线、总览、异常、两种卡片、最后一行计数。
- 4 种展开视图。
- 上面的写法细则和信号建议表。

**范围外**

- 判断状态、检测信号：用 line-health 的结果。
- 解析用户回复、转达答复：归 decision-queue。
- `/flow` 的源头诊断和 `/lines`、`/item`：归 query-commands。
- 把文字发到哪里：由收件枢纽会话直接输出。
- 需求第 6.3 节第 7 条「提出方未合成组合」：本模块看不出几个独立的小选择是否该合成组合，所以不做判断，选项照原文列出。

## 接口约定

```python
from decision_inbox import view

text = view.render(g, now="...", assessment=result, relay=agents_snapshot)  # 主视图 Markdown
view.render_detail(g, item=12)            # 「12 详情」
view.render_waits(g, now="...", relay=agents_snapshot)  # 「看等待」
view.render_closed(g, day="2026-10-16")   # 「看已关闭」
view.render_invalidated(g)                # 「看失效」
```

- `assessment` 是 line-health 的 `Assessment`；`relay` 用来给「等你确认」卡片取 detail 和开始时间，可以为 None（这时卡片不写括号和时间）。
- 待答事项、等待单、已关闭和失效的数据，从 decision-queue、wait-tickets 已有的读取函数取，本模块不另读状态文件。

## 依赖

- 本插件模块：review-registry（标签已存进事项里，本模块只读）、decision-queue（待答、失效、最近转达）、wait-tickets（等待单与计数）、line-health（状态与信号），以及 group-store 的名册（短名）。
- 外部组件：无。

## 测试策略

- 用 group-store 临时组和前面模块的样例构造事项、等待单和信号；时间全部显式传入。
- 主视图做一份完整的期望文本（覆盖第一行推送、等你确认卡片、普通卡片、异常、计数），逐字比较；其余细则逐条断言。

## 边界

- **始终**：按固定顺序；每张卡片最多一个复制块；「选了会怎样」只从原文摘；主视图不出现消息编号和路径。
- **先问**：改变固定顺序或卡片样式；在主视图里加新的行。
- **绝不**：替提出方补后果、改写或合并选项；自己判断状态或信号。

## 验收标准

1. 没有任何事项、异常、等待时：输出只有各线、「等你决定 0 项 · 异常 0」、最后一行计数三部分。
2. 完整场景的主视图与上面的样例逐字一致（样例里代码块那一行，换成真正的 Markdown 代码块）。
3. 有信号 1 时，第一行是「⚠ 全线停住 N 分钟：卡在 X」。X 按已定事项 5 的规则选出；选不出时写「卡在哪见 /flow」。
4. 「等你确认」的会话：计入「等你决定 N 项」，卡片排在所有事项卡片前面；没有 detail 时不写括号。
5. 卡片：推荐选项排第一并标「推荐」；全卡只有一个代码块；复制块按已定事项 8 处理字母不重复、去掉「你该回」开头猜的编号；没有推荐时没有代码块、也没有「推荐」字样；选项超过 30 字截断；缺后果的选项写「提出方未说明后果」；多线事项来源写「多线：前端＋API」；挡住 0 条线时标题里不出现「挡住」。
6. 审查行：「审查中，请勿先批」加粗；「⚠ 未标审查」下面有「正文提到：」行。
7. 「刚转达」只列 10 分钟内转达的事项；11 分钟前的不列。
8. 时间写法：59 分钟写「59 分钟前」，60 分钟写「1 小时前」，25 小时写「1 天前」。
9. 异常行：信号 2～10 各自按信号建议表写出一行；信号 1 不在异常区重复。
10. 展开视图：
    - 「详情」含原文全文和 agent-relay 消息编号；
    - 「看等待」每张单一行，带提醒标记；
    - 「看已关闭」带理由和依据；
    - 「看失效」列出已取代和已撤回的事项。
11. 主视图里不出现 agent-relay 消息编号和文件路径（测试扫描输出）。

## 假设

1. 收件枢纽会话把本模块的输出原样显示给用户，Claude 桌面版能渲染 Markdown 代码块并提供复制按钮。
2. 一个协作组同时等你决定的事项是个位数到十几项，主视图不分页。
